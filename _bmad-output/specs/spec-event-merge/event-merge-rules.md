# 事件合并规则

## 1. 处理顺序

```text
来源达到触发门槛
        ↓
生成子 Event Context Pack
        ↓
跨来源匹配
├─ 高置信同一事件 → 合并后路由一次
└─ 未达到自动合并门槛 → 升格为独立 Event，正常向下路由
```

这里的“高置信”是指通过全部合并硬门槛且 `merge_confidence >= 0.95`。未达到自动合并门槛包括进入人工复核、低置信匹配和命中硬冲突；这些情况不丧失来源已经取得的响应资格。

1. 热搜榜、未来事件和主题圈分别判断自身触发门槛。
2. 达到门槛的来源独立生成来源子 Event Context Pack。
3. 事件管理使用子包召回候选主 Event。
4. 系统先检查合并硬门槛，再计算综合置信度。
5. 系统执行自动合并、人工复核或保持独立。
6. 合并后根据主 Event 的响应状态决定任务影响。

## 2. 合并硬门槛

只有全部满足以下条件，才允许计算综合置信度：

| 维度 | 合并资格 | 硬冲突示例 |
|---|---|---|
| 主体 | 指向同一个规范化主体；别名、缩写和跨语言名称可以归一 | OpenAI 与 Anthropic |
| 核心动作 | 动作相同或语义等价 | 计划发布与正式发布 |
| 对象 | 指向同一个具体产品、政策、比赛、数据发布或现实事项 | 同主题下的两个不同产品 |
| 时间 | 精确时间相同、日期相同、时间范围重叠，或官方日程能证明指向同一安排 | 不同场次、批次或已确认的改期前后 |
| 状态 | 传闻、预期、确认、进行中、完成、取消或否认等状态相同或兼容 | 预计发生与已经取消 |
| 核心事实 | 对谁、做什么、作用于什么和何时发生不存在互斥描述 | 一方确认发生，另一方官方否认 |

地点缺失或表达粒度不同不构成硬冲突；地点明确互斥且会改变事件身份时，禁止自动合并。

## 3. 综合置信度

通过硬门槛后，各维度取 `0–1`：

| 维度 | 权重 |
|---|---:|
| 主体一致度 | 20% |
| 核心动作一致度 | 25% |
| 对象一致度 | 20% |
| 时间兼容度 | 15% |
| 地点兼容度 | 5% |
| 事件状态与事实含义一致度 | 15% |

```text
merge_confidence =
  subject_score × 0.20
  + action_score × 0.25
  + object_score × 0.20
  + time_score × 0.15
  + location_score × 0.05
  + state_meaning_score × 0.15
```

| 结果 | 处理 |
|---|---|
| 命中任一硬冲突 | 禁止自动合并 |
| `merge_confidence >= 0.95` | 自动合并 |
| `0.80 <= merge_confidence < 0.95` | 保持独立并正常路由，同时进入人工复核 |
| `merge_confidence < 0.80` | 保持独立 Event 并正常路由 |

人工复核必须展示字段对比、各维度分数、支持依据、冲突点以及对候选和已发布内容的影响。

## 4. 未合并事件路由

来源达到自身触发门槛后即取得独立响应资格。跨来源匹配只负责判断是否去重，不构成新的响应门禁：

| 匹配结果 | Event 处理 | 下游处理 |
|---|---|---|
| `merge_confidence >= 0.95` | 自动归入同一主 Event | 由主 Event 路由一次 |
| `0.80 <= merge_confidence < 0.95` | 暂时保持独立并进入人工复核 | 各自正常路由，不等待复核 |
| `merge_confidence < 0.80` | 创建或保持独立 Event | 各自正常路由 |
| 命中硬冲突 | 创建独立或关联 Event | 各自正常路由 |

人工复核与下游响应并行进行。系统必须保留候选合并关系，以便运营人员稍后确认合并时收敛任务和后续响应。

## 5. 合并结果

- 复用唯一主 Event，并把新子包追加到对应来源上下文。
- 保留原始子包、触发依据、触发时间、规则版本和 Evidence 关系。
- 相同 Evidence 可以去重展示，但不得删除来源和支持关系。
- 不同来源上下文不得互相覆盖。
- 来源增加不改变 Confirmation Level；确认等级只能由合格 Evidence 和核验结果改变。
- 新子包不得因合并而重复创建相同账号响应任务。

## 6. 后到来源与响应状态

| 主 Event 状态 | 新来源情况 | 处理 |
|---|---|---|
| 尚未响应 | 任一来源首次触发 | 合并完成后创建一次默认响应 |
| 已有未发布候选 | 只增加来源或热度 | 更新上下文，保留候选 |
| 已有未发布候选 | 改变重要 Evidence、确认状态或表达边界 | 标记重新预检 |
| 已有未发布候选 | 出现核心事实冲突 | 冻结受影响候选，进入人工复核 |
| 已发布 | 同类来源再次触发 | 只更新该来源上下文，不提醒、不新建任务 |
| 已发布 | 首次新增来源类型 | 合并上下文并产生一次运营提醒，不自动生成或发布 |
| 已发布 | 新信息与发布版本冲突 | 保持发布记录不变，产生复核提醒 |

来源自身的触发门槛负责判断是否值得关注。事件管理不再计算“明显热度跃迁”，只判断该来源类型是否首次命中主 Event。

## 7. 任务唯一性

默认响应任务的唯一边界为：

```text
Main Event × Account × Skill Version
```

合并来源不会创建第二个相同任务。运营人员收到首次新增来源提醒后，可以主动创建有明确目的的跟进响应；该人工动作必须保留与原响应的关系和原因。

### 7.1 人工晚合并

两个独立 Event 已经向下游路由后，运营人员仍可确认其属于同一现实事件。合并时按任务状态处理：

| 重复响应状态 | 晚合并处理 |
|---|---|
| 尚未创建任务 | 不再创建重复任务 |
| 任务已创建但尚未开始 | 取消重复任务，保留主 Event 任务 |
| 已生成候选但尚未发布 | 冻结重复候选并标记“合并待处理”，由运营人员选择保留内容；不得静默删除 |
| 已发布 | 发布记录和原 Context Pack 版本保持不变，并关联到合并后的主 Event |

晚合并完成后，默认响应只能从主 Event 继续发起。原 Event、任务、候选、发布记录和人工决定均保留审计关系。

## 8. 独立关联 Event

以下变化不是来源补充，应建立独立关联 Event：

| 变化 | 关系建议 |
|---|---|
| 新动作 | 后续进展 |
| 计划正式发生 | 正式落地 |
| 新结果公布 | 结果 |
| 改期或取消 | 变更 |
| 官方修正原口径 | 更正 |
| 事实发生反转 | 反转 |
| 长期议题出现阶段性动作 | 主/子事件或后续进展 |

关联 Event 可以引用必要背景，但必须拥有独立事实、时间、状态、触发记录、Context Pack 和响应任务。

## 9. 验收场景

- **AC-1 自动合并：**Given 未来事件和热搜子包通过全部硬门槛且置信度为 `0.96`，When 后到子包进入事件管理，Then 系统复用同一主 Event、追加来源上下文且不重复创建账号任务。
- **AC-2 人工复核：**Given 两个子包通过硬门槛且置信度为 `0.88`，When 系统完成匹配，Then 二者保持未合并并进入人工队列，页面展示维度分数、依据和影响。
- **AC-3 硬冲突：**Given 两个子包主题相同但核心动作分别为“计划发布”和“正式发布”，When 系统匹配，Then 禁止自动合并并建议建立“正式落地”关系。
- **AC-4 迟到来源：**Given 未来事件已经触发并发布，When 同一事实首次达到热搜门槛，Then 系统追加热搜上下文并只产生一次运营提醒，不自动生成或发布。
- **AC-5 同类更新：**Given 主 Event 已记录热搜触发，When 热搜排名再次变化，Then 系统只更新热搜上下文，不产生提醒或新任务。
- **AC-6 候选保护：**Given 主 Event 存在未发布候选，When 后到来源改变表达边界，Then 系统保留候选历史并将当前候选标记为需要重新预检。
- **AC-7 发布不可变：**Given 内容基于 Context Pack V1 已发布，When 新来源使主 Event 更新到 V2，Then 发布记录继续引用 V1，且系统不得重写历史内容。
- **AC-8 新事实发展：**Given 已有“预计发布”Event，When 来源报告“正式发布”，Then 系统创建独立关联 Event，而不是把正式发布吞并为来源补充。
- **AC-9 复核不阻塞：**Given 两个来源分别达到触发门槛且匹配置信度为 `0.88`，When 系统将其送入人工复核，Then 两个独立 Event 均正常向下游路由，不等待人工决定。
- **AC-10 低分独立路由：**Given 两个来源分别达到触发门槛且匹配置信度低于 `0.80`，When 匹配结束，Then 系统保留两个独立 Event 并分别建立响应任务。
- **AC-11 晚合并收敛：**Given 两个 Event 已分别路由且一个存在未发布候选、另一个已有发布记录，When 运营人员确认晚合并，Then 系统冻结重复未发布候选、保留发布版本并将后续默认响应收敛到主 Event。
