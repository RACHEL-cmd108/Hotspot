# 内容厨房产品与 Agent 规格

状态：Draft v0.1
更新日期：2026-09-02
适用对象：产品、UX、前端、后端、内容生成 Agent 开发者
视觉基线：_bmad-output/planning-artifacts/ux-designs/ux-hotspot-monitor-2026-08-13-dashboard-task-center-v2/DESIGN.md

## 1. 产品边界

内容厨房承接上游 Event Workspace 已完成的事实整理、运营机会判断和 Angle 选择，将它们转化为可发布内容。

内容厨房不重新判断事件是否值得响应，也不重新选择内容角度。用户在这里完成四件事：

1. 选择这次发布想实现的目标。
2. 确定内容说给谁听，以及采用哪种表达方式。
3. 选择内容形式、辅助能力并填写补充要求。
4. 生成候选稿，与 AI 协作修改，人工确认最终内容。

## 2. 全局规则

- 四个步骤允许前进和后退，返回后保留此前选择及用户输入。
- 保存并退出时保存当前步骤、全部选择、草稿和 AI 修改历史。
- 上游事实、Angle 和风险边界只读继承，内容厨房不得静默改写。
- 推荐是可编辑的预填结果，用户可以取消或替换。
- 所有 AI 结果都是建议，未经用户确认不得成为最终稿。
- 第三步使用现有已确认版面，不改变信息结构和交互。

## 3. Step 1：发布目标

### 3.1 页面文案

标题：发这条内容，你最想实现什么？

说明：选择这次发布最重要的目标，最多选择 3 个。你也可以添加自己的目标。

### 3.2 内置目标

| 目标 | 给用户的解释 |
|---|---|
| 把事情讲清楚 | 让更多人快速了解发生了什么 |
| 提供有用判断 | 帮读者判断该怎么看、怎么选 |
| 分享观点和分析 | 解释背后的原因、影响或趋势 |
| 教会一个方法 | 提供步骤、教程或可执行清单 |
| 引发讨论 | 鼓励回复、引用或表达不同观点 |
| 引导采取行动 | 引导关注、订阅、报名或使用产品 |

### 3.3 选择规则

- 目标支持多选，不区分主要目标和补充目标。
- 最少选择 1 个，最多选择 3 个。
- 系统根据上游 Event、Angle、运营机会和事实边界推荐一个或多个目标。
- 推荐目标进入页面时默认选中。
- 用户可以取消推荐、替换推荐或增选其他目标。
- 每个推荐目标的卡片内直接显示一行推荐理由。
- 推荐理由必须引用真实上游依据，不能使用空泛解释。
- 用户尝试选择第 4 个目标时，不加入选择，并就地提示：最多选择 3 个目标，请先取消一个目标。

推荐理由示例：

> 推荐提供有用判断，因为当前采用的角度是开发者迁移判断清单。

### 3.4 自定义目标

- 页面提供“添加自定义目标”入口。
- 用户只填写一句自然语言，不需要分别填写名称和描述。
- 系统根据用户原句生成可编辑的简短展示标签。
- 用户原句完整保留，并传给内容生成 Agent。
- 默认仅用于当前内容。
- 用户主动选择“保存为常用目标”后，写入个人目标库。
- 个人常用目标可在后续内容厨房中选择、编辑和删除。

示例：

- 用户输入：希望读者看完后，重新检查团队当前的模型迁移计划。
- 页面标签：重新检查迁移计划。
- Agent 输入：保留用户填写的完整原句。

## 4. Step 2：目标读者与表达人设

### 4.1 页面文案

标题：这条内容说给谁听？用哪种表达方式？

说明：先选择目标读者，再选择一种表达人设。两项都可以使用预设或自行添加。

### 4.2 目标读者

内置目标读者：

- AI 开发者
- 产品经理 / 创业者
- 普通科技用户
- 已有社群用户

选择规则：

- 必须指定 1 个主要读者。
- 可以额外选择最多 2 个次要读者。
- 内容生成 Agent 优先保证主要读者能够理解并获得价值。
- 次要读者只影响术语解释和背景补充，不得稀释主要读者的内容焦点。
- 系统根据上游 Angle 和事件内容默认选中 1 个主要读者。
- 系统可以推荐次要读者，但不自动选中。
- 推荐读者直接显示基于真实上游信息的推荐理由。

页面展示示例：

- AI 开发者 · 主要读者
- 产品经理 / 创业者 · 次要读者

### 4.3 自定义目标读者

- 页面提供“添加目标读者”入口。
- 用户用一句自然语言描述想说给谁听。
- 系统自动生成可编辑的简短标签。
- 主页面只展示短标签和主要/次要角色。
- 用户点击自定义标签时，可以查看和修改完整描述。
- 完整描述传给内容生成 Agent。
- 默认仅用于当前内容。
- 用户主动选择“保存为常用读者”后，写入个人读者库。

示例：

- 用户输入：正在评估是否迁移 GPT-6 API 的中小团队技术负责人。
- 页面标签：中小团队技术负责人。

### 4.4 账号 Content Skill

这里的“表达人设”实际指项目已有的账号 Content Skill，不再新增独立的“表达人设 Spec”对象。

一个 Content Skill 是基于对标账号、账号历史内容、领域知识和其他研究资料形成的可运行 Skill。它不只是文风模板，还负责：

- 账号的核心身份、关注领域和内容价值。
- 哪类 Event 应参与、观察或跳过。
- 采用事实模式、归因讨论模式或观点延展模式。
- 适合主帖、Thread、回复、引用帖、事实卡、教程或分析中的哪些形式。
- 账号独有的选题角度、叙事结构、写作 DNA 和互动方式。
- 如何使用 Event Context Pack、Content Insight 和其他允许的上下文。
- 账号专属表达禁区和风险约束。
- 生成、修改、自检和输出候选的执行流程。

权威内容以该 Skill 包中的运行时 SKILL.md 为准。对标账号研究、样例拆解、正反例和详细规则放在 Skill 的 references 或其他配套文件中，由 SKILL.md 按需引用。

### 4.5 Content Skill 包建议结构

每个账号 Skill 至少包含：

1. SKILL.md：触发条件、核心身份、参与判断、执行流程、写作规则、风险边界和输出要求。
2. references/benchmark-research.md：对标账号与其他研究资料。
3. references/content-patterns.md：Hook、结构、节奏、内容形式和互动机制。
4. references/examples.md：经过筛选的正面示例、反面示例及分析。
5. references/domain-rules.md：该账号领域的专属术语、判断框架和限制。
6. evals/：用于检查参与判断、事实边界、账号差异和内容质量的测试案例。

如果某个 Skill 的规则较少，可以合并 references 文件，但 SKILL.md 仍然必须是唯一运行入口。

### 4.6 内容厨房中的使用方式

- 页面只展示已安装且可用的 Content Skill。
- 内置项和用户项本质上都是 Skill，只是来源不同。
- 卡片展示 Skill 名称、账号或角色、一句话定位、版本和来源。
- 系统根据 Event、Angle、发布目标、目标读者和内容形式推荐一个 Skill。
- 用户每次选择一个 Skill，也可以选择“不加载账号 Skill”的中性生成。
- “添加我的人设”支持粘贴 Markdown 内容或上传 .md 文件。
- 系统解析 Markdown，识别账号身份、关注领域、参与判断、内容形式、写作 DNA、表达禁区、事实处理规则和示例。
- 系统先展示解析摘要，由用户确认后再加载到当前内容任务。
- 解析时不得补造 Markdown 中没有表达的账号规则；缺失项必须标记为“未识别”。
- 用户可以返回修改原 Markdown 后重新解析。
- 用户可以选择“仅本次使用”或“保存到我的 Skill”。保存后进入个人 Skill 库，可在后续内容厨房中复用。
- 如果导入内容已经是符合运行约定的 SKILL.md，系统保留其完整内容并生成版本与内容哈希。
- 如果导入内容是自由格式的人设研究文档，系统将解析结果包装为可运行的临时 Skill 快照；保存到 Skill 库前必须由用户确认。
- 创建、深度编辑、测试和发布正式 Skill 可以在独立的 Skill 管理流程中继续完成。
- 内容厨房可以填写“本次补充要求”，但该要求只影响当前内容，不自动回写 Content Skill。
- 内容任务保存实际使用的 Skill ID、版本和内容哈希，后续更新 Skill 不改变历史任务。

#### Markdown 导入流程

1. 用户点击“添加我的人设”。
2. 用户选择粘贴 Markdown 或上传 .md 文件。
3. 系统解析文档并显示处理中状态。
4. 系统展示人设名称、一句话定位、主要领域、表达特点、内容形式、禁区和未识别项。
5. 用户确认解析结果，或返回修改 Markdown 后重新解析。
6. 用户选择“仅本次使用”或“保存到我的 Skill”。
7. 系统加载确认后的 Skill 快照，并返回内容厨房第二步。

解析失败时保留用户粘贴的原文，说明失败原因，并允许重试。解析成功不等于自动选中或保存，必须经过用户确认。

#### 待设计展开态

第二步点击“添加我的人设”后，需要展开独立的完整交互界面，而不是只出现一个文件上传控件。该展开态至少覆盖：

- 粘贴 Markdown 与上传 .md 两种入口。
- 原文输入、文件状态和解析中状态。
- 解析结果摘要与未识别项。
- 返回修改、重新解析、仅本次使用、保存到我的 Skill 并使用。
- 解析失败、文件不支持和内容为空状态。

具体采用当前页面内展开、侧边面板还是模态窗口，留待后续结合第二步整体版面单独设计；在视觉稿确认前，开发不得自行假定最终布局。

### 4.7 页面示例

可供选择的卡片可以是：

- AI / Tech 快讯 Skill
- 通用热点快讯 Skill
- 官方账号 Skill
- Nate Silver 内容 Skill
- 我的开发者 KOL Skill
- 不加载账号 Skill
- 添加我的 Skill

其中“快讯”“官方账号”等是用户看得懂的页面名称，背后加载的是完整 Content Skill 包。

## 5. Step 3：内容形式与辅助能力

本步骤保持当前已确认版面和交互，不重新设计。

### 5.1 主要成品

- X 短帖
- X Thread
- 回复 / 引用帖
- 图文事实卡
- 短视频脚本
- 长文 / Newsletter

主要成品为单选。

### 5.2 辅助能力

- 补充可信依据
- 给配图文案
- 找一个更有讨论度的开头
- 生成英文版本
- 严格检查风险表达

辅助能力支持多选。补充要求为自由文本。

## 6. Step 4：生成并修改

### 6.1 页面目标

用户直接编辑候选稿，或者通过 AI 修改选中内容和全文。最终内容由用户人工确认。

标题：生成并修改内容

说明：直接编辑候选稿，或让 AI 修改选中内容和全文。

### 6.2 候选稿

- 默认生成 2 个候选稿，使用“候选 1 / 候选 2”切换。
- 候选稿可以直接编辑。
- 用户的直接编辑即时保存为当前工作版本。
- 切换候选稿不会丢失另一候选稿的修改。
- 用户可以基于当前候选再生成一个版本。

说明：候选数量 2 是当前推荐默认值，可根据生成成本调整为 3。

### 6.3 AI 修改入口

界面提供：

- 快捷指令：开头更直接、压缩篇幅、加强判断、调整语气、检查事实边界。
- 自然语言输入框：告诉 AI 你想怎么修改。
- 选中文字后，默认修改选中部分。
- 未选择文字时，默认修改全文。
- 用户可以明确切换“修改选中内容 / 修改全文”。

### 6.4 AI 修改结果

- AI 返回修改建议，不直接覆盖正文。
- 局部修改必须展示原文和建议修改。
- 全文修改必须提供修改摘要，并允许查看差异。
- 用户可以选择“应用修改”或“忽略”。
- 应用修改后产生一个新版本。
- 用户可以撤销最近一次应用，或从版本历史恢复。
- 忽略修改不改变正文。

### 6.5 加载、失败和冲突

- 生成中显示“正在根据你的要求修改”，正文保持可见但避免同时覆盖同一段。
- 请求失败时保留用户指令和当前正文，提供重试。
- 当用户等待 AI 时又编辑了同一段，AI 结果返回后标记为冲突，不自动应用。
- 风险检查发现问题时，在建议中明确指出问题位置和原因。

### 6.6 最终采用

- “标记采用”前必须有一份当前候选稿。
- 用户点击后生成只读 Final v1。
- 标记采用不等于自动发布。
- Final v1 投递到内容发布流程。
- 如需继续修改，应返回内容厨房并生成新版本。

## 7. Agent 输入契约

每次首次生成应包含：

| 字段 | 含义 |
|---|---|
| eventContext | 上游 Event 事实与来源 |
| angle | 已采用的内容角度 |
| riskBoundaries | 不可越过的事实和表达边界 |
| goals | 用户最终选择的 1 到 3 个目标 |
| primaryAudience | 主要读者的标签和完整描述 |
| secondaryAudiences | 0 到 2 个次要读者 |
| contentSkill | 当前选中的 Content Skill ID、版本、内容哈希与运行入口 |
| contentFormat | 第三步选择的主要成品 |
| assistCapabilities | 第三步选择的辅助能力 |
| additionalRequirements | 用户补充要求 |

AI 修改请求额外包含：

| 字段 | 含义 |
|---|---|
| currentDraft | 当前完整草稿 |
| selectedText | 用户选中文字，没有则为空 |
| selectionRange | 选中文字在正文中的位置 |
| instruction | 用户快捷指令或自然语言要求 |
| editScope | selection 或 full |
| baseVersion | 发起修改时的版本号 |

## 8. Agent 输出契约

首次生成返回：

- 候选稿 ID
- 完整正文
- 使用的目标、读者、人设和内容形式
- 引用的事实依据
- 风险检查结果

AI 修改返回：

- 修改范围
- 原文
- 建议文本
- 修改摘要
- 风险提示
- 应用建议后的完整正文
- 基于的版本号

Agent 不得：

- 静默改变上游事实。
- 把待确认信息写成既成事实。
- 未经用户确认直接覆盖正文。
- 未经用户确认标记为最终稿。
- 为满足多个目标而忽略主要读者。

## 9. 保存的数据

一次内容厨房会话至少保存：

- 当前步骤
- 上游 Event 和 Angle 引用
- 已选目标及推荐理由
- 主要和次要读者
- 当前 Content Skill ID、版本和内容哈希
- 内容形式、辅助能力和补充要求
- 全部候选稿
- 用户直接编辑记录
- AI 修改请求和结果
- 应用、忽略和撤销记录
- 当前工作版本
- 最终采用版本

保存引用的 Content Skill 版本快照，避免用户后来修改 Skill 时改变历史内容。

## 10. 验收标准

### Step 1

- 可以选择 1 到 3 个目标。
- 推荐目标默认选中并直接展示真实推荐理由。
- 第 4 个目标不会加入选择，并显示明确提示。
- 可以用一句话添加自定义目标。
- 自定义目标可仅本次使用或保存复用。

### Step 2

- 必须有 1 个主要读者，可添加最多 2 个次要读者。
- 默认主要读者来自上游推荐。
- 推荐的次要读者不自动选中。
- 自定义读者在页面显示短标签，并保留完整描述给 Agent。
- 可以选择系统内置 Skill，也可以加载用户自己的 Skill。
- 每次只应用 1 个 Content Skill，或者明确选择不加载账号 Skill。

### Step 3

- 版面和已有交互保持不变。
- 主要成品单选，辅助能力多选，补充要求可编辑。

### Step 4

- 正文可直接编辑。
- 选中文字后可局部 AI 修改。
- 未选择文字时可修改全文。
- AI 建议不会直接覆盖正文。
- 用户可查看修改差异并选择应用或忽略。
- 应用后可撤销或从版本历史恢复。
- AI 请求失败或版本冲突不会丢失当前正文。
- 最终内容必须人工确认后才能标记采用。

### 全流程

- 前进和返回不会丢失选择、输入或草稿。
- 保存并退出后可以恢复到原步骤。
- 上游事实、Angle 和风险边界全程可追溯。
- 标记采用只创建 Final 版本，不自动发布。

## 11. 当前采用的推荐默认值

以下规则由产品逻辑补齐，尚未逐项向用户确认，但可以作为第一版实现默认值：

1. 每次只能使用 1 个 Content Skill，或者选择不加载账号 Skill。
2. 用户已有的 Skill 通过 Skill 库安装或导入，不在内容厨房内创建。
3. 系统内置 Skill 不能直接覆盖，只能复制后修改并发布为新版本。
4. 初次生成 2 个候选稿。
5. AI 应用修改后保留版本历史和撤销能力。
6. 标记采用生成 Final v1，但不自动发布。

这些默认值不阻塞原型和开发，后续可以通过配置调整。
