# 热点运营系统详细业务规则（最终结论版）

> 版本日期：2026-08-13
> 文档性质：本轮规则讨论的最终决策汇总
> 内容边界：仅记录最终结论，不记录讨论过程；已整合突发热点响应、运营排期、内容任务、营销活动、异常与效果追踪规则。

## 1. 总体目标与自动化边界

系统的核心目标是同时处理突发热点和可预见事件：把满足触发条件的 X 热点快速转化为可供人工发布的内容，并通过运营排期提前监测、预热和准备重要未来事件。

主链路为：

`X 榜单采集 → 触发判断 → Event 形成与核验 → Event 关联 → 多账号响应 → 内容预检 → 待发布 → 人工复制发布 → URL 回填 → 数据追踪 → 已完成事件库 / 复盘优化`

运营排期链路为：

`事件源接入 / 人工导入 → 标准化与去重 → 确认与时间精度 → 持续监测 → 行动评分与窗口建议 → Event Context Pack → 下游按需处理 → 实时 Event 关联 → 结果跟进与复盘`

统一边界如下：

1. 普通排名触发、重点主题触发和跨区异动触发均自动进入完整响应流程。
2. 正常链路在候选内容交付前不设置人工参与、人工审批或“是否参与”决策门。
3. 系统负责发现、归并、核验、关联、生成、预检、异常监测和数据追踪。
4. 人工主要负责选择候选、修改内容、复制发布、回填 URL、放弃响应和处理异常。
5. 系统不自动向 X 发布内容。
6. `T0` 只表示系统首次成功发现合格触发；当前不规定 `T0` 到自动校验完成的最长时限。
7. 热点经过检验和校准后立即触发内容生成，不设置一个人为等待的“5 分钟投递动作”。

## 2. X 榜单采集规则

### 2.1 采集范围

首期固定采集以下五个 X 榜单：

1. Worldwide
2. United States（美国）
3. United Kingdom（英国）
4. Japan（日本）
5. Korea（韩国）

每个榜单采集 Top 30，共计最多 150 个榜单条目。

### 2.2 采集频率与快照

1. 榜单 API 每小时调用一次。
2. 只有成功采集的结果可以形成排名快照。
3. 每次快照至少保存榜单、地区、热搜词、当前排名和采集时间。
4. 排名变化以相邻两次成功小时快照比较。
5. 采集失败不产生虚假的排名变化，也不形成新的触发判断。
6. 重点主题和跨区 Event 不提高榜单采集频率，仍使用小时快照。

## 3. Signal 触发规则

### 3.1 普通排名触发

满足任一条件即自动触发：

1. 某个具体 Event 首次进入任一目标榜单前 5。
2. 同一 Event 在相邻两次成功小时快照之间排名上升至少 10 位。

“一小时内上升 10 位”是指两次相邻小时快照之间的观察变化，不要求平台提供原生热度曲线。

### 3.2 重点主题触发

1. 重点主题是行业和产品相关的宽泛主题，例如 AI、加密监管、预测市场或体育赛事。
2. 热搜中通常出现的是具体 Event，而不是主题名称本身。
3. 只要具体 Event 在语义上属于某个已配置重点主题，即视为命中。
4. 例如“GPT-5 发布”可属于“AI”主题，即使热搜词中没有单独出现“AI”。
5. 命中重点主题后不等待“前 5”或“上升 10 位”，立即进入完整自动响应。
6. 明显匹配由系统自动确认；无法确定的主题归属进入人工校正或异常处理。
7. “目标群体中热度很高”的监测源尚未接入，本期不作为触发条件。

### 3.3 跨区异动触发

1. 同一具体 Event 同时出现在至少两个目标地区榜单时，标记为跨区异动。
2. 跨区异动不是单纯标红或排序加权，而是直接触发完整自动响应。
3. 不要求它同时满足前 5、上升 10 位或重点主题条件。
4. 地区扩散信息进入 Event 和内容上下文，例如“该事件正在从美国扩散至英国”。

## 4. 热搜依据与一句话事实摘要

### 4.1 帖子获取

1. 对每个进入处理的榜单条目，读取 X 返回的默认热门排序。
2. 使用默认排序中实际可取得的前 3 条帖子。
3. 不自定义互动分数，不重新排序。
4. 如果实际只能取得 1 条或 2 条，则按实际数量处理，不补齐、不阻塞响应。

### 4.2 事实边界

1. 三条热门帖子能够证明“这些说法正在 X 上传播”。
2. 三条帖子不能当然证明其描述的现实事件一定为真。
3. 系统生成的一句话摘要必须与当前依据的确定程度一致。
4. 未确认信息必须使用“多个热门帖子称”“X 上正在讨论”等归属表达。
5. 不得把观点、猜测、传闻或模型推断写成确定事实。

### 4.3 核验结论

核验结果只使用三种易理解状态：

- `信息一致`：取得的帖子对核心事实描述一致。
- `信息有限`：取得的信息较少，当前没有明显冲突。
- `存在冲突`：不同帖子对核心事实存在不一致说法。

存在冲突时不停止自动响应，但内容必须说明当前有哪些不同说法，不能任选一种写成确定结论。

## 5. Event Card 规则

### 5.1 基础字段

Event Card 至少包含：

1. Event 标题。
2. 一句话事件事实摘要。
3. 当前排名与排名变化。
4. 所属地区。
5. 首次发现时间。
6. 命中原因：前 5、急剧上升、重点主题、跨区异动等。
7. 事实依据按钮。
8. 核验结论。
9. 当前响应状态。

### 5.2 依据展示

1. 页面不展开账号、互动数据或帖子摘要。
2. 链接以“依据 1 / 依据 2 / 依据 3”按钮展示。
3. 点击按钮打开对应原帖。
4. 单地区 Event 最多保存该地区 3 条帖子。
5. 多地区 Event 为每个地区最多抓取 3 条帖子，去重后合并保存。
6. 同一帖子出现在多个榜单时只保存一次，但保留其榜单来源关系。

### 5.3 热度监测

Event Card 可展示：

- 各地区当前排名。
- 各地区历史最高排名。
- 排名变化趋势和小时快照曲线。
- 当前出现的地区。
- 跨区信号数量。
- 最近更新时间。
- 当前热度状态。

热度曲线由系统连续调用 API 并保存快照形成，X 当前快照本身不等同于系统历史曲线。

第一次发现时没有系统历史曲线，但前 5、重点主题或跨区异动仍可立即触发，不等待后续快照。

## 6. Event 归并、新建与关联

### 6.1 同一个 Event

核心事实没有变化，只是以下内容不同，仍属于同一个 Event：

- 所在榜单或地区不同。
- 热搜词或语言不同。
- 发现时间不同。
- 排名不同。
- 被热搜榜、重点主题或跨区模块重复发现。
- 不同帖子对同一核心事实采用不同表达。

同一个 Event 只更新地区、排名、依据和热度信息，不重复触发相同内容生成。

### 6.2 独立的新 Event

出现以下任一变化时，创建独立的新 Event：

- 新动作。
- 新结果。
- 新状态。
- 新的公开口径。
- 事实更正或反转。
- 预告转为正式发生。

例如：

- “OpenAI 预告将发布新模型”与“OpenAI 正式发布新模型”是两个 Event。
- “GPT-6 发布”与“GPT-6 开放 API”是两个关联 Event。
- “OpenAI 发布模型”与“Kimi 开源模型”仅属于同一宽泛主题，不是关联 Event。

系统不覆盖旧 Event，也不修改已经发布的旧内容。新状态以新 Event 独立响应。

### 6.3 Event 关系类型

可使用以下关联类型：

- 前置事件。
- 后续进展。
- 正式落地。
- 结果公布。
- 口径更正。
- 事件反转。

### 6.4 关联 Event 选择

1. 程序先按主体、对象、语义关键词和时间关系从数据库召回少量候选 Event。
2. 大模型只在候选集合中判断，不无限遍历数据库。
3. 只有属于同一具体发展线、且能帮助理解当前状态的 Event 才能建立关联。
4. 最多选择 3 条最相关历史 Event。
5. 少于 3 条时按实际数量提供，不为凑数强行关联。
6. 当前内容生成时，以当前 Event 为主，历史 Event 只提供必要上下文。
7. 新旧事实冲突时，内容应使用“此前……目前……”明确表达变化。

### 6.5 非事实变化

Event 已生成内容后仅出现以下变化时，不自动重新生成：

- 新增地区。
- 排名变化。
- 热度继续上升或下降。
- 形成跨区异动但核心事实未变。
- 出现更多重复同一说法的帖子。

系统只更新 Event Card；人工可手动要求 AI 使用最新上下文重新生成。

## 7. 账号响应体系

系统采用“基础响应层 + 人设响应层”。

### 7.1 基础响应层

基础层包含：

1. 快讯型账号。
2. 事件解释翻译型账号。
3. 产品承接型账号。

快讯型和解释翻译型对每个触发 Event 固定生成；产品承接型对每个 Event 固定判断，但不固定生成。

### 7.2 快讯型账号

职责：快速、准确地转述当前核心事实。

规则：

1. 覆盖所有触发自动响应的 Event，不限制新闻类别。
2. 每个 Event 固定生成 3 条原创快讯候选。
3. 每条只讲一个核心事实，通常为 1 至 2 句话。
4. 优先写清楚谁、做了什么、对象或结果是什么。
5. 重要数字、时间或地区可前置。
6. 不做深入分析，不表达个人观点，不关联产品。
7. 三条候选只改变信息排列、句式和简洁程度，不改变事实。

标签规则：

- `快讯 / JUST IN`：新出现的明确事件或状态。
- `LIVE`：事件正在进行。
- `UPDATE`：当前 Event 是历史发展线的新状态。
- `BREAKING`：仅用于影响重大且事实明确的事件。
- 信息有限或存在冲突时不得使用 `BREAKING`。

该账号后续配置独立的全品类快讯 Skill，借鉴 WatcherGuru 的短、快、单一事实机制，但不继承其金融加密类别限制。

### 7.3 事件解释翻译型账号

职责：帮助普通用户理解事件，而不是简单把快讯写长。

最小业务边界：

1. 覆盖每个触发 Event。
2. 补充必要背景。
3. 将专业概念翻译成普通用户能理解的表达。
4. 解释为什么受到关注，以及当前已知、未知和后续观察点。
5. 可读取最多 3 条关联 Event 作为上下文。
6. 不负责产品承接。
7. 不为了增加长度而添加无依据推测。
8. 每个 Event 固定生成 3 条候选。
9. 单条解释、长帖或线程由其内容生成 Skill 决定。

### 7.4 产品承接型账号

职责：判断当前 Event 能否被产品自然承接。

输入必须包含：

- 当前 Event 与事实边界。
- 产品特性和目标用户。
- 已上线功能。
- 当前可用预测市场、页面或活动。
- 链接和可用状态。
- 未上线或禁止宣传的能力。

判断结果：

#### 直接承接

产品存在与 Event 直接相关且当前可用的预测市场、功能、页面或活动。

处理：

- 生成 3 条候选。
- 可明确说明产品价值。
- 可使用系统提供的真实链接。
- 可引导用户查看、判断或参与。

#### 自然相关

没有一一对应的专门页面，但产品现有一般能力确实能服务由 Event 产生的用户需求，且提及产品不生硬。

处理：

- 生成 3 条候选。
- 可从产品定位、使用场景或判断需求切入。
- 不得声称已有专门市场或页面。
- 不得添加虚假行动入口。
- 产品只是事件后的自然延伸，不能抢占事件主体。

#### 无关

产品不能帮助用户理解、判断或参与该 Event，或者必须强行插入品牌才能建立关系。

处理：不生成产品内容，并返回不承接原因。

产品数据边界：

1. 产品资料由人工预先写入系统或由产品接口提供。
2. 大模型不得编造市场、概率、价格、功能、活动、链接或可用状态。
3. 产品资料不足时标记`产品资料不足`，不生成。
4. 产品承接账号绑定可配置的内容生成 Skill，可在系统设置中新增、更换或修改。

## 8. 九个人设账号规则

### 8.1 基本机制

九个人设 Skill 是账号的运营规则，不是单纯的文风模板。

处理流程：

1. 核验后的 Event 分别交给九个账号 Skill。
2. 大模型读取 Event 和当前账号 Skill。
3. 每个 Skill 独立判断是否参与。
4. 决定参与后，由 Skill 自行确定响应角度和行动形式。
5. 决定不参与时跳过，不影响其他账号和基础账号。

### 8.2 响应行动

人设账号可选择：

- 原创短帖。
- 原创长帖或线程。
- 引用转发。
- 评论回复。
- 观察。
- 跳过。

如果采用引用转发或评论回复，必须返回真实目标原帖链接；没有合适目标时改用原创或跳过。

### 8.3 候选内容

1. 决定参与的账号生成 3 条候选。
2. 同一 Event 可以被多个账号响应。
3. 不同账号可以使用相近角度，但必须符合各自定位和受众。
4. 不要求九个账号全部生成。
5. 系统统一账号返回的结果标签，例如是否参与、角度、行动、目标原帖和候选内容。
6. “统一输出格式”只统一系统所需字段，不统一内容的语气、长度或结构。

## 9. 候选内容与 AI 编辑

### 9.1 待发布区

1. 每个参与账号生成的 3 条候选全部进入该账号待发布区。
2. 人工从中选择 1 条进入发布。
3. 同一账号对同一个 Event 默认只能有 1 条进入发布。
4. 选中一条后，其他两条暂时不能选择。
5. 正式发布前可以取消选择，恢复三条可选状态并改选其他内容。
6. 选定并成功发布后，其余候选标记为未采用。
7. 关联的新 Event 视为新的响应，可再次生成和发布。

### 9.2 AI 交互窗口

待发布区内提供围绕当前 Event 和账号的 AI 编辑窗口：

1. 用户可以不填写要求，直接重新生成。
2. 用户可以输入“更短”“换个角度”“不要提产品”等修改要求。
3. 用户可以选中单条候选继续修改。
4. AI 同时读取当前 Event、最多 3 条关联 Event、账号 Skill、原候选和用户要求。
5. 重新生成默认仍返回 3 条候选。
6. 用户要求不能改变已核验事实，也不能突破风险规则或账号 Skill。
7. 旧内容保留在版本历史中，待发布区默认展示最新一轮。

## 10. 系统级风险框架

五类风险全系统共用：

### 10.1 平台规则风险

包括但不限于暴力威胁、仇恨、骚扰、自残鼓励、未成年人性内容、隐私泄露、冒充、误导媒体、垃圾营销、诈骗、恶意链接、非法交易、版权或商标侵权。

### 10.2 事实风险

包括把传闻写成事实、错误人物或数字、过期信息、不同说法未解决却写成唯一结论，以及超出 Event 事实边界的内容。

### 10.3 法律风险

包括未经证实的犯罪、欺诈、内幕交易等指控，以及诽谤、版权和监管限制风险。

### 10.4 品牌风险

包括消费灾难或伤亡、攻击群体、生硬蹭热点、明显违反品牌定位或可能造成严重负面认知的表达。

### 10.5 产品与金融风险

包括编造产品能力、市场、概率、价格或收益，暗示稳赚或保证回报，忽略地区、资格或产品可用性限制。

所有账号、Skill、营销活动方案及未来扩展业务均适用。业务和账号可以配置更严格规则，但不能降低系统底线。

### 10.6 风险等级

- `低风险`：正常生成和进入待发布区。
- `中风险`：可以生成，但待发布区显示简短风险提示并采用谨慎口径。
- `高风险`：只生成内部参考草稿，禁止复制发布，等待人工处理。
- `禁止生成`：无法安全改写的严重违规内容不生成草稿，只保留 Event 和命中原因。

### 10.7 高风险人工处理

运营负责人或系统维护人员可以选择：

1. 解除限制，并重新预检。
2. 要求修改内容，并重新预检。
3. 禁止发布，并关闭该次内容响应。

解除限制不代表原内容可直接发布。所有选择必须记录操作人、时间、原因和处理意见。

## 11. 内容预检规则

### 11.1 五层预检

每条候选在后台依次完成：

1. 平台合规检查。
2. 事实一致性检查。
3. 法律与品牌检查。
4. 产品信息检查。
5. 发布行为检查。

### 11.2 实现分工

- 固定规则和关键词库拦截明确违规或禁用表达。
- 大模型判断隐含语义、上下文、指控、冒犯和生硬关联。
- Event 数据核对人物、动作、结果、数字、时间和核验口径。
- 产品数据库核对产品能力、市场、价格、概率、链接和状态。
- 程序检查 URL、账号、目标原帖、内容相似度和重复发布行为。

### 11.3 失败与重新生成

1. 预检失败内容不进入正常待发布区。
2. 系统根据失败原因立即自动修改或重新生成该条。
3. 最多自动尝试 3 次。
4. 只有通过预检的候选正常展示给用户。
5. 正常页面不展示完整检查过程和模型推理。
6. Event 风险或无法交付规定数量时，只展示简要原因和处理入口。

### 11.4 候选不足

3 次后不足 3 条合格候选即属于异常：

- 有 1 至 2 条合格候选：保留并展示，但暂停发布，等待人工处理。
- 没有合格候选：不进入待发布区。

人工可以：

1. 接受现有 1 至 2 条并恢复发布。
2. 继续要求系统生成。
3. 放弃本次响应。

### 11.5 复盘记录

每次生成保留完整版本链：

`初始版本 → 命中规则 → 自动修改/重生成 → 再次预检 → 最终版本 → 人工采用/放弃`

至少记录：

- Event 和账号。
- 账号 Skill 及版本。
- 原始候选。
- 风险类别和具体规则。
- 触发风险的文案片段。
- 系统处理动作。
- 修改后内容。
- 最终结果。
- 人工编辑、采用或放弃。
- 各步骤时间。

这些记录回填至复盘优化模块。高度敏感内容必须脱敏。复盘只能提出规则或 Skill 优化建议，未经人工确认不能修改线上规则。

## 12. 内容时效与关联新进展

1. 旧候选不因新 Event 自动删除或改写。
2. 发现关联新 Event 后，旧候选标记`已有新进展`。
3. 旧候选默认暂停直接发布，需要人工确认。
4. 人工可以继续发布、编辑后发布、放弃或转到新 Event。
5. 如果旧候选与最新事实直接冲突，标记`内容可能已失效`并禁止直接复制。

## 13. 人工发布与 URL 回填

### 13.1 发布流程

1. 用户选中候选后进入待发布状态。
2. 页面显示完整内容和复制按钮。
3. 用户复制内容并前往 X 手动发布。
4. 系统不自动跳转完成发布，也不调用账号自动发帖。
5. 发布后用户回到系统回填结果。

### 13.2 回填结果

- `发布成功`：填写 X 帖子 URL。
- `发布失败`：选择失败状态并填写原因。

### 13.3 URL 校验

1. 系统预先配置允许使用的 X 账号。
2. URL 必须属于当前内容对应的配置账号。
3. 格式错误、账号不匹配或重复 URL 不能提交。
4. 页面在提交时直接提示具体错误。
5. URL 校验成功后才关联 Event、账号和被选候选。
6. 首期不设计删帖和帖子编辑后的复杂状态变化。

发布失败不占用“同账号同 Event 只能发布一条”的名额；人工可以重新选择、编辑或重新生成后再次尝试。

## 14. 营销活动规则

### 14.1 活动机会入口

命中以下任一信号时，系统可主动推荐活动：

1. 重大可预见事件。
2. 竞品或行业活动。
3. 自有产品或品牌里程碑。
4. 具有清晰参与机制的当前热点。

不要求所有条件同时满足。每个 Event 同时保留人工主动“探索活动”的入口，即使系统没有主动推荐。

### 14.2 三个活动候选

活动探索固定生成 3 个候选。每个候选包含：

- 活动名称。
- 核心机制。
- 与 Event 的匹配理由。
- 目标。
- 目标受众。
- 渠道。
- 时间。
- 当前就绪程度。
- 关键准备缺口。

三个候选必须在活动机制上明显不同。用户不满意时可整批重新生成。

### 14.3 能力缺口

1. 系统可以推荐“值得做但当前还缺能力”的活动形式。
2. 必须清晰标明产品能力、页面、预算、奖励、集成、资源或负责人缺口。
3. “重大可预见事件”允许在产品承接尚未完善时提前生成方案。
4. 生成建议不代表已经批准或可以立即上线。

### 14.4 完整活动方案

用户选定一个候选后，系统只交付完整方案，不继续代替人工执行。方案包括：

1. 活动概述。
2. 目标与希望推动的用户行为。
3. 目标受众。
4. 参与机制和规则。
5. 内容概念。
6. 渠道和可选合作。
7. 产品承接路径。
8. 时间线。
9. 资源和准备清单。
10. 风险与边界。
11. 建议效果指标。
12. 当前缺口和下一步人工工作。

不得编造预算、奖励、产品能力或确定结果；不负责创建项目、分配人员、审批预算、实现功能或上线活动。

## 15. KOL 当前版本边界

1. 首期不建设独立 KOL 业务界面。
2. KOL 只作为营销活动方案中的一种推广建议。
3. 系统设置中由人工导入和维护产品相关 KOL 数据，包括覆盖、性价比等指标。
4. 活动方案可根据活动目的推荐合适 KOL 和合作形式。
5. 系统不自动发送触达私信。
6. 系统不管理报价、关系推进或合作执行。
7. 可以预留未来独立 KOL 窗口，但不进入当前版本。

## 16. 全链路监测与失败回流

### 16.1 监测环节

系统监测：

1. 榜单抓取。
2. 热门帖子获取。
3. Event 识别与归并。
4. 一句话摘要。
5. Event 关联。
6. 基础账号内容生成。
7. 人设账号响应。
8. 后台内容预检。
9. 待发布状态。
10. URL 回填。
11. 效果数据抓取。

每个环节至少保留：

- 当前状态。
- 开始与完成时间。
- 失败原因。
- 重试次数。
- 影响范围。
- 人工处理入口。

### 16.2 自动重试

1. 技术失败从失败环节立即重试，不从头重新运行。
2. 最多自动重试 3 次。
3. 任意一次成功后，从当前环节继续下游流程。
4. 已成功数据必须保留。
5. 单账号失败不阻塞其他账号。
6. 实际可取得帖子不足 3 条是正常降级，不算技术失败。
7. 预检不通过属于内容异常，按内容重生成规则处理，不按接口故障处理。

### 16.3 人工升级

连续 3 次技术重试失败后：

1. 状态升级为`需要人工处理`。
2. 通知运营负责人。
3. 异常持续展示在运营总览看板，直到恢复或人工关闭。
4. 页面显示失败环节、原因、次数和影响范围。
5. 人工可重新执行、补充信息、跳过该环节或终止本次响应。
6. 成功恢复后标记`已恢复`并继续下游流程。
7. 当前不规定再次催办时间和强制处理期限。

## 17. 响应完成与已完成事件库

### 17.1 账号响应完成

某个账号满足以下条件后完成：

1. 一条候选已由人工发布。
2. 有效 URL 已正确关联 Event、账号和候选。
3. 系统已建立数据追踪，或发布完成但数据追踪被独立标记为异常。

### 17.2 Event 响应完成

Event 满足以下条件后进入已完成事件库：

1. 所有参与账号均进入`已完成`或`放弃发布`终态。
2. 至少一个账号已发布并回填有效 URL。
3. 如果所有账号都放弃，Event 标记`已关闭—未发布`，不算响应完成。

### 17.3 长期未发布

1. 候选生成后长期未发布，系统持续在运营看板展示和催办。
2. 人工可继续处理或点击“放弃本次响应”。
3. 放弃后记录操作人和原因，并进入`已关闭—未发布`。
4. 当前不设置自动关闭期限。

### 17.4 已完成事件库展示

列表至少展示：

- Event 标题和摘要。
- 发布账号数量。
- 已发布内容数量。
- 发布时间。
- 汇总互动数据。
- 最近数据变化。
- 数据最后更新时间。

详情展示：

- 每个账号发布的内容与原帖链接。
- 各帖数据表现和变化曲线。
- 放弃发布或未采用的账号结果。
- 触发、生成、预检、发布和回填记录。
- 关联 Event。

## 18. 发布效果追踪

### 18.1 抓取频率

1. 发布后前 24 小时：每 2 小时抓取一次。
2. 24 小时以后：每 5 小时抓取一次。
3. 默认至少追踪 7 天。

### 18.2 指标

必须展示：

- 点赞。
- 回复。
- 转发。

接口支持时同时记录：

- 引用。
- 浏览量。

### 18.3 表现良好与延长追踪

1. 发布后 48 小时内浏览量达到 1000，判定为表现良好。
2. 表现良好的内容将追踪期从 7 天延长至 14 天。
3. 1000 浏览量、48 小时判断窗口和 14 天追踪期均为系统配置项。
4. 配置项可在后续直接修改，无需改写业务代码。
5. 每条内容记录实际使用的规则版本。

### 18.4 数据接口异常

1. URL 有效回填后，发布状态记为`已完成`。
2. 数据接口不可用时，数据状态单独记为`追踪异常`。
3. 追踪异常不推翻内容已经发布的事实，也不阻止 Event 进入已完成事件库。
4. 系统立即重试 3 次，仍失败则通知运营负责人并显示在总览看板。
5. 人工可重新执行或暂时忽略；后续成功抓取后标记`已恢复`。

## 19. 权限、配置与版本治理

### 19.1 最小权限划分

- 普通运营人员：选择和编辑候选、重新生成、复制发布、回填 URL、记录失败、放弃响应、处理一般异常。
- 运营负责人：解除高风险限制、修改重点主题和监测配置、调整排期窗口、校正排期事件、提前启动任务、处理升级异常。
- 系统维护人员：管理账号 Skill、风险规则、排期来源、行动评分、接口和系统配置，也可处理高风险限制。

### 19.2 版本记录

以下对象必须版本化：

- 重点主题和监测规则。
- 风险规则。
- 内容预检规则。
- 账号 Skill。
- 产品资料与承接配置。
- 效果追踪阈值、判断窗口和追踪期限。
- 运营排期来源及字段映射。
- 排期证据、去重和状态规则。
- 行动评分维度、阈值和状态映射。
- 监测、预热、事件进行和结果跟进窗口。

每次修改至少记录：修改前、修改后、修改人、修改时间、原因和生效范围。

### 19.3 生效规则

1. 新规则默认只用于修改后新进入的 Event 或新发布内容。
2. 已经在处理或追踪中的对象继续使用启动时的旧版本。
3. 不允许规则变更静默覆盖历史判断。
4. 复盘优化产生的建议必须人工确认后才能形成新版本。

## 20. 运营排期规则

“运营排期”用于管理尚未发生、预计发生或时间尚待确认，但值得提前持续监测和准备的事件。它不负责替代实时热点监测，也不把宽泛主题本身当成一个未来事件。

### 20.1 事件源

首版 P0 只使用下列五个来源；官方入口是 Evidence Record 的默认来源，聚合站不可替代它。

| 来源 | 官方入口 | 接入与频率 | 筛选与默认处理 |
|---|---|---|---|
| OPM 美国联邦假日 | https://www.opm.gov/policy-data-oversight/pay-leave/federal-holidays/ | 首次一次性录入或 CSV；年度刷新时同步一次 | 仅当年剩余假日；`Fixed`、`Date`、`factual` |
| BEA 发布时间表 | https://www.bea.gov/news/schedule | 每日同步一次，解析官方表格 | 仅当年剩余发布；来源明确日期/时间时为 `Confirmed` 与相应精度 |
| BLS 发布日历 | https://www.bls.gov/schedule/news_release/bls.ics | 每日同步一次，解析 iCalendar | 仅 Employment Situation、CPI、PPI、JOLTS、ECI，且只取当年剩余日期；`Confirmed` |
| FOMC 会议日历 | https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm | 每日同步一次，解析当前年份会议日期 | 仅当年剩余会议；`Confirmed`、`Date range`；使用 FOMC 会议模板 |
| 人工导入 | 系统表单或 CSV | 提交后即时校验和写入 | 行业大会、品牌节点、特定人物行程等；来源链接必填，默认 `Needs verification` |

P1 为重点体育官方赛程与监管连接器；P2 为企业 IR 观察和 SEC 确认，均不属于首版开发范围。未接通 Connector 必须显示`未启用`或`等待配置`，不得展示模拟同步结果。

首版事件池只导入当前自然年剩余时间的事件，不做未来多年的规则展开或跨年度事件池。进入下一自然年时，通过年度刷新导入当年剩余事件。

### 20.2 来源接口与系统设置

每个排期来源至少配置：

- 来源名称和来源类型。
- 来源 URL、API、iCal、CSV/Excel 或其他接入方式。
- 认证方式和授权状态。
- 同步频率。
- 原始字段到系统字段的映射。
- 时区和日期格式。
- 超时、最多 3 次技术重试和降级方式。
- 最近成功同步时间、来源健康和数据新鲜度。
- 来源失效时的人工补录入口。

官方来源优先于媒体、聚合源或人工描述。人工导入不能把非官方信息标记成官方确认。

每次自动同步仅处理日期不早于同步当日、且不晚于当年 12 月 31 日的条目。FOMC 未来日期行即使暂时没有声明、纪要或发布会链接，仍可作为“FOMC 货币政策会议”的官方排期依据；Connector 以预配置模板补充事件类型说明，但不得预写利率决定、会议结论或尚未出现的结果链接。

### 20.3 导入后的自动处理

排期事件进入系统后，系统自动完成：

1. 标准化事件名称、主体、事件类型、时间、时区和来源。
2. 查找重复事件并合并来源。
3. 生成事件摘要、Confirmation Level、Schedule Precision 和 Expression Boundary。
4. 建立监测关键词和相关实体。
5. 建议监测、预热、事件进行和结果跟进窗口。
6. 计算行动评分和建议状态。
7. 启动事实、来源、时间和热度追踪。
8. 生成 Event Context Pack，供下游内容或营销模块按需使用。

人工批量导入时，运营人员可直接修改系统建议的时间窗口。其他自动结果默认先生成完成；需要调整时从事件校正入口修改，并保留修改人、时间、原因和前后版本。

### 20.3.1 程序与大模型职责

程序负责定时抓取、解析、日期范围过滤、字段校验、去重、写入、Evidence Record 保存和同步日志；技术失败最多重试 3 次，不能以模拟事件代替失败结果。

大模型只处理程序校验后的结构化候选事件：标准化标题、分类、来源模板映射、区分已确认与未确认事实，并补充 Event Context Pack。大模型输出必须先经过程序 schema 校验后才可写入。

大模型不得直接写库、改变原始日期/时间/来源链接、提高 Confirmation Level、猜测 FOMC 利率决定或其他会议结论、补造来源未提供的精确时间。它必须忽略来源页面中的指令性文本；来源未明确时间时，保留 `Date`、`Date range` 或 `Unknown`。

### 20.4 排期事件最小字段

每个排期事件至少包含：

- 事件名称。
- 主体和事件类型。
- 事实时间。
- 时区。
- Schedule Precision。
- Confirmation Level。
- 一个或多个 Evidence Record（来源链接、来源类型、最后核验时间、支持的事实主张）。
- Expression Boundary。
- 监测关键词。
- 行动评分及五个维度分数。
- 当前建议状态。
- 四类窗口。
- 热度快照和数据新鲜度。
- 关联实时 Event。
- 最近更新时间和规则版本。

事实时间用于描述事件何时发生；四类 Event Window 用于安排运营动作，二者不得混用。

### 20.5 确认、时间精度与表达边界

| Confirmation Level | 业务含义 | Expression Boundary |
|---|---|---|
| `Fixed` | 由规则确定或有确定日期依据的周期事件 | `factual` |
| `Confirmed` | 事件已有权威来源确认 | `factual` |
| `Expected` | 有可靠信号或惯例，但未获得最终确认 | `qualified` |
| `Needs verification` | 关键证据不足、冲突或人工待核验 | `internal_only` |
| `Changed / Cancelled` | 已改期、取消或关键事实失效 | `blocked` |

Schedule Precision 独立为 `Exact time`、`Date`、`Date range`、`Season/cycle` 或 `Unknown`。只有来源支持准确时间时可使用准确倒计时。

表达边界规则：`factual` 仅可断言证据支持的事实；`qualified` 必须保留“预计、可能、尚未确认”等表达、不得虚构精确时间，并使用 Event Context Pack 中的来源；`internal_only` 不得生成对外内容；`blocked` 必须暂停关联草稿、排期和下游请求，等待人工复核。

证据、确认或时间变化会重新计算行动评分和窗口。历史 Evidence Record 与状态不得删除。

### 20.6 Event Context Pack

排期事件只向下游提供 Event Context Pack，包含事件说明、当前状态、已确认与未确认事实、Evidence Record、事实时间、Event Window 和 Expression Boundary。它不规定下游必须产出多少内容、用什么渠道或形式发布，也不要求创建营销活动。

### 20.7 去重与合并

满足以下条件时，多个来源归并为同一个排期事件：

1. 主体相同。
2. 计划动作或事件类型相同。
3. 指向同一场发布、数据公布、比赛、节日或官方活动。
4. 日期、时间范围或官方日程可以相互对应。

处理规则：

- 标题或语言不同但指向同一件事，合并。
- 官方日历、人工导入和其他来源指向同一事件，合并并保留全部去重后来源。
- 同一主题下的不同发布、比赛或数据公布，不合并。
- 出现新的动作、结果、正式落地或口径时，创建独立实时 Event 或新的排期事件，并建立关联。
- 官方新口径成为当前采用口径，但旧来源和变更历史保留。

### 20.8 进入排期后的持续监测

事件一进入运营排期，即开始持续监测：

- 官方时间、地点、参与方和安排变化。
- 关键事实与来源状态。
- 相关关键词和实体。
- X 榜单及其他已接入讨论来源。
- 热度快照和相对基线变化。
- 是否出现与该排期事件匹配的实时 Signal。

不单独设置需要用户理解或操作的“准备窗口”。进入排期本身就代表系统已经建立完整追踪；进入预热窗口时，系统更新 Event Context Pack 并提高相关监测与准备优先级。

没有连续数据时，只显示当前快照并标记`热度历史不足`。系统不得为了展示曲线而虚构历史热度。

### 20.9 行动评分

行动评分满分 100 分：

| 维度 | 分值 | 默认判断口径 |
|---|---:|---|
| 事件影响力 | 0–25 | 事件对目标用户、行业、产品和大众讨论的潜在影响；重大宏观、选举、世界杯或核心行业事件高于普通纪念日 |
| 证据可靠度 | 0–25 | 官方一手来源、事件是否确认、时间是否确认以及来源是否冲突 |
| 热度动量 | 0–25 | 近 1/6/24 小时讨论相对基线的变化；跨区扩散或快速增长提高分数 |
| 时间紧迫度 | 0–15 | 距离预热、事件发生或结果窗口的时间；越接近当前需要执行的窗口，分数越高 |
| 内容可执行性 | 0–10 | 是否存在明确角度、可引用事实、素材、适配账号和真实产品承接 |

默认分档：

| 总分 | 状态 | 系统动作 |
|---:|---|---|
| 0–39 | 观察 | 持续监测事实、时间和热度 |
| 40–59 | 储备 | 完善关键词、Evidence Record 和事件上下文 |
| 60–74 | 计划 | 更新预热建议和 Event Context Pack |
| 75–89 | 激活 | 提高监测和准备优先级，可向下游提供上下文包 |
| 90–100 | 立即响应 | 最高优先级核验和准备，可触发下游按自身规则处理 |

评分是系统建议，不是不可覆盖的审批门禁。运营人员可提前启动、调整窗口或继续观察，但必须记录原因。评分规则变更只影响新计算结果，历史分数和所用版本保留。

Action Score 只表示当前运营优先级，不代表事件发生概率，也不因 Confirmation Level 被强行封顶。评分不会升级 Expression Boundary；高热 `Expected` 仍必须使用 `qualified` 表达。

### 20.10 四类窗口

系统为每个排期事件自动建议：

1. `监测窗口`：事件进入排期后立即开始，持续跟踪事实、来源、时间和热度。
2. `预热窗口`：开始识别账号、准备情景内容、检查产品承接并允许发布事件前期内容。
3. `事件进行窗口`：事件正在发生或官方信息正在发布，实时更新与快讯响应优先。
4. `结果跟进窗口`：结果、数据、赛果或正式落地后，生成解释、结果和后续影响内容。

系统自动建议窗口，运营人员可以修改。修改后：

- 下游未开始的请求按新窗口重新评估。
- 进行中的下游请求标记`窗口已变化`并重新检查事实状态与表达边界。
- 已发布内容不修改，但可关联变更记录。
- 所有变化记录修改人、原因、版本和影响范围。

### 20.11 预热与下游处理

进入预热窗口后，系统自动更新 Event Context Pack、加强事实和热度监测，并将上下文包提供给下游模块。下游内容模块或营销模块可按自身请求和规则生成草案或方案；运营排期本身不自动规定内容数量、账号、渠道、形式或是否创建营销活动。`internal_only` 和 `blocked` 状态不得生成对外内容。

排期事件仍保留在运营排期中；下游处理不等于事件已经发生，也不等于内容已发布。

### 20.12 与实时 Signal 和 Event 的关系

当 X 榜单或其他实时来源出现与排期事件匹配的 Signal 时：

1. 系统以排期事件的主体、事件类型、关键词和时间窗口进行候选召回。
2. 核心事实相同且只是新增来源时，补充当前排期事件或已存在 Event 的依据，并更新 Event Context Pack。
3. 出现新的动作、结果、正式落地、口径变化或事件反转时，创建独立实时 Event。
4. 新 Event 进入`事件管理`，并将排期事件和最多 3 条相关历史 Event 作为内容上下文。
5. 旧排期事件、旧 Event 和已发布内容均不覆盖或改写。
6. 对相同核心事实的下游请求必须复用或更新上下文，避免重复生成与重复发布。

### 20.13 改期、取消和时间确认

- `时间确认`：更新事实时间、Schedule Precision、Evidence Record、倒计时、评分和窗口。
- `改期`：保留原时间和来源记录，标记 `Changed / Cancelled` 并重算窗口；暂停关联草稿和下游请求，人工复核后恢复。
- `取消`：标记 `Changed / Cancelled`，暂停关联草稿、排期和下游请求；可生成“事件已取消”的新实时 Event 或更新内容。
- `提前发生`：立即结束等待并进入事件进行或立即响应状态。
- `长期未确认`：保持观察或储备，不自动使用确定口径。

### 20.14 营销活动与 KOL

运营排期是营销活动的重要主动入口：

1. 重大可预见事件可以在产品承接尚未完善时提前生成方案。
2. 系统固定生成 3 个机制明显不同的活动候选，不满意可整批重新生成。
3. 候选和完整方案沿用第 14 章规定的字段、风险和交付边界。
4. KOL 只作为活动方案中的可选合作建议，使用系统已导入的 KOL 数据。
5. 系统只交付方案，不代替人工审批预算、实现功能、上线活动、联系 KOL 或执行合作。

### 20.15 页面展示与操作

运营排期以月历为主要视图，至少展示：

- 本月事件、Fixed/Confirmed、Expected、Needs verification 和进入预热数量。
- 按类别、Confirmation Level、来源和准备状态筛选。
- 日期上的具体事件和当前状态。
- 证据与来源。
- 行动评分和窗口。
- 热度热力图与趋势。
- 查看 Event Context Pack 与 Expression Boundary。
- 按需进入下游内容或营销模块。

页面只承担未来事件的排期与准备。已经形成的实时 Event 进入`事件管理`；账号候选、选择、发布和 URL 回填进入`内容发布`。

### 20.16 异常处理

排期来源同步、字段解析、时间转换、去重、评分和 Event Context Pack 更新均纳入全链路监测：

1. 技术失败从失败环节立即重试，最多 3 次。
2. 三次失败后通知运营负责人并进入运营总览异常看板。
3. 单个来源失败时保留其他成功来源和已生成结果。
4. 来源冲突属于 `Needs verification`，不按接口故障处理。
5. 人工可补充来源、校正字段、重新同步、跳过来源或关闭排期事件，所有操作留痕。

## 21. 已明确延期或独立定义的事项

以下内容不由本文强行补值：

1. `T0 → 自动校验完成`的最长时间。
2. 异常通知后的再次提醒时间和强制处理期限。
3. 独立 KOL 业务界面和自动触达。
4. 私域触达的完整业务规则。
5. P1/P2 来源连接器的具体 API、同步频率和授权方案。

## 22. 最终状态摘要

本轮已经明确的系统工作方式是：

> 系统同时处理突发热点和未来排期。突发链路每小时采集 X 五榜 Top 30；普通前 5、小时上升 10 位、重点主题命中或跨区异动均自动形成响应。运营排期把规则库、官方日历、官方赛程、政策监控和人工导入事件统一经过 Evidence Record、确认等级、时间精度、监测、100 分行动评分和四类窗口，形成受 Expression Boundary 约束的 Event Context Pack，并在实时 Signal 出现时关联独立 Event。两条链路最终共享账号响应、风险预检、人工发布、URL 回填、数据追踪、异常处理和复盘优化规则。
