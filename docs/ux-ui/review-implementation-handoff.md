# UX/UI 实施交接审查

- **审查镜头**：BMad UX — 实施交接（开发、架构和 Story 拆分的下游消费者）
- **审查范围**：`docs/ux-ui/ux-00` 至 `ux-07`、`assets/`、可点击原型，以及用于追溯的 PRD v2.4-draft
- **审查日期**：2026-08-10
- **方式**：只读审查；本报告不改变现有 UX/UI 决策

## 总体结论

当前文档已经清晰表达了产品方向：M1–M5、双层工作台、Event 主链、四类 M4 行动，以及“系统内部权威、连接器可替换”的边界。它适合继续开展产品讨论和高保真探索。

但它**尚不能作为开发可无猜测实施的 UX 交接基线**。阻塞点不在视觉风格，而在页面级合同、M1/M2 状态与权限、完整流程图、以及文档/原型/资产三者的一致性。开发者现在需要自行猜测页面是否独立、状态何时变化、谁可执行何种操作、何时显示何种恢复入口。

### 发现汇总

| 严重级别 | 数量 | 含义 |
|---|---:|---|
| Critical | 2 | 未关闭前，不应进入架构定稿或 Story 拆分。 |
| High | 6 | 会造成跨角色、跨模块或主流程实现不一致。 |
| Medium | 6 | 会在联调、验收或扩展时引入显著返工。 |
| Low | 2 | 追溯或维护瑕疵，应随本轮修订关闭。 |

## Critical

### C-01 缺少逐页、可实施的页面规格

**位置：**[ux-04 §4.1](./ux-04-pages-and-wireframes.md#41-页面清单)、[ux-04 §4.4](./ux-04-pages-and-wireframes.md#44-共同页面框架)。

**证据：**页面清单仅提供“ID、页面、核心任务、追溯”四列。共同页面框架只描述了全局导航与三栏宽度。17 个页面没有分别说明进入条件、必须数据、主/次操作、成功后的去向、加载/空/失败/权限受限行为、离开时保存规则，以及页面与组件/图稿的稳定引用。

**下游影响：**同一 `PG-04 Event 工作区` 可以被实现成单页、多个 Tab 或多个路由；`PG-13 Action Task / Receipt 看板` 也无法确定是任务列表、任务详情还是回执详情。开发、测试与 Story 拆分会形成不同理解，无法写出可验证验收条件。

**修复：**在 `ux-04` 为每个 PG 建立统一规格表，至少包含：

| 必填字段 | 要回答的问题 |
|---|---|
| 目标与主要角色 | 谁为什么来到这里；不同角色看到什么。 |
| 进入/离开 | 来源页面或通知；成功、取消、返回分别去哪里，是否保持筛选和滚动。 |
| 必须展示的数据 | 对象标识、更新时间、来源、口径、状态、风险、窗口等。 |
| 核心操作与门禁 | 可做什么、前置条件、确认文案、成功结果。 |
| 页面状态 | 冷加载、空、筛选无结果、部分成功、失败、权限受限、过期。 |
| 追溯与资产 | UJ/FR/CE/BE、相关 UX-F/UX-R、线框/高保真/原型路径。 |
| 阶段 | 完整产品、Phase 0 优先、后续启用；阶段标签不改变完整功能定义。 |

### C-02 M1/M2 的页面边界与正式设计资产不闭合

**位置：**[ux-02 §2.2](./ux-02-information-architecture.md#22-页面地图)、[ux-04 §4.1–4.3](./ux-04-pages-and-wireframes.md#41-页面清单)、[ux-04 §4.2 第 32 行](./ux-04-pages-and-wireframes.md#42-原型覆盖策略)、[ux-04 §4.3](./ux-04-pages-and-wireframes.md#43-关键高保真)。

**证据：**

- `PG-03` 将“实时雷达与候选”并在同一编号下，但没有定义雷达榜单、Candidate 队列、Candidate 详情/合并拆分分别是页面、抽屉还是同页视图。
- `PG-16` 把未来事件中心、共享业务字典、连接器与两类 Telegram 目标目录放在同一页面编号；这是彼此独立的业务工作区和管理工作区。
- FR-04 的“监控范围与提醒”没有独立 IA/PG 表面；在 [ux-07 §7.4](./ux-07-accessibility-and-validation.md#74-fr-逐条追溯) 被映射到 `PG-03/15`，其中 `PG-15` 是异常中心，不是提醒配置或合并规则的管理表面。
- [ux-04 §4.2](./ux-04-pages-and-wireframes.md#42-原型覆盖策略) 宣称 Phase 0 高保真覆盖 `PG-03`，但 [§4.3 的资产表](./ux-04-pages-and-wireframes.md#43-关键高保真) 没有 `PG-03` 对应图稿；雷达目前只存在于 HTML 原型。

**下游影响：**M1/M2 是所有行动的输入。页面边界不固定时，路由、权限、数据加载粒度、缓存、Story 边界与验收范围都无法确定；“完整产品原型包含所有功能”的目标也没有可审计的页面覆盖表。

**修复：**先完成页面清单重构，再写细节。至少分出：热点雷达、Candidate Event 队列、未来事件中心、监测范围与提醒、Event 工作区、Event Card/版本、Fact/Evidence 来源抽屉或工作区、事件监测视图、配置与业务字典。若有意使用 Tab/抽屉而非独立页面，必须在各 PG 规格中明确载体、URL/深链规则和返回行为。

## High

### H-01 M1—M3 状态机缺失，无法实现候选、事件和机会的合法流转

**位置：**[ux-05 §5.1](./ux-05-interaction-and-states.md#51-分对象状态表达)；对照 [PRD §6.3](../product-requirements/prd/prd-06-business-and-data-rules.md#63-状态规则)。

**证据：**UX 只定义了 Task Plan、Execution Deliverable Draft、Action Task、Task Receipt 的状态。PRD 明确的 Candidate Event（新建/待形成/已形成/已忽略/已合并）、Event（待核验/监测中/待决策/已关闭/再激活）和 Opportunity（待评估/四档决策）在 UX 中没有状态视觉、允许转换、触发角色、禁用动作、过期/再激活或异常恢复规则。

**下游影响：**开发者不能确定“合并后是否可拆分”“关闭事件从哪里再激活”“证据不足时是否可创建 Opportunity”“观察何时回流”等主流程行为；这些正是 UJ-1—UJ-3 的关键验收。

**修复：**在 `ux-05` 追加 M1–M3 状态矩阵。每个转换写明：来源状态、目标状态、触发人/自动规则、所需理由/确认、UI 表现、可撤销性、通知对象、阻止下游动作及恢复入口。再把状态 ID 引到相应 PG 页面规格。

### H-02 角色只描述“关注点”，没有权限与字段可见性的实施矩阵

**位置：**[ux-01 §1.3](./ux-01-design-goals-and-foundations.md#13-角色与责任)、[ux-04 §4.5](./ux-04-pages-and-wireframes.md#45-跳转与权限)、[ux-05 §5.9](./ux-05-interaction-and-states.md#59-页面基础状态)；对照 [PRD §6.4](../product-requirements/prd/prd-06-business-and-data-rules.md#64-权限与决策权)。

**证据：**UX 列出了角色的默认关注与关键动作，并说明“角色只改变默认视图、敏感字段和操作权”，但没有给出操作级权限矩阵。例如谁可合并/拆分 Candidate、校正 Fact、选定 Task Plan、批量审核、批准 Telegram 外部目标、创建/取消 Action Task、重试连接器、批准策略回写，以及无权者能看到哪些对象标识、敏感字段和申请入口，均未落实。

**下游影响：**前端隐藏按钮与后端授权无法对齐；审核与高风险边界尤其容易出现“看得见但不该操作”或“有权却找不到入口”。

**修复：**在 `ux-05` 或专门权限附录中提供“角色 × 对象 × 动作 × 可见字段 × 批量权限 × 申请/升级路径”矩阵，继承 PRD §6.4 的业务决策权。所有 PG 规格引用适用权限组，并定义 `permission-denied` 的最小上下文。

### H-03 大多数 UJ/UX-F 仍是文字摘要，缺少可交接的主流程、分支与恢复图

**位置：**[ux-03 §3.2—§3.11](./ux-03-user-flows.md#32-ux-f02-完整产品行动主链)、[ux-03 §3.12](./ux-03-user-flows.md#311-恢复路径)；对照 [GUIDE UX/UI 验收标准](../../GUIDE.md#ux-ui)。

**证据：**仅 UX-F01 有 Mermaid 图。UX-F02 至 UX-F11 均为一两段文字或内联箭头；`UX-R01—09` 是恢复表而不是从失败点返回主链的流程图。UJ-1 的重复/异常来源、UJ-2 的改期/取消/匹配不足、UJ-3 的事实冲突/观察/再评估、UJ-4 四种行动的审核与交接、UJ-5 的缺失结果与策略批准都没有明确的条件分支、责任人、状态变化和页面跳转。

**下游影响：**无法据此拆分端到端 Story、设计通知/升级、或判定异常后的返回页面和数据状态。

**修复：**按 UJ-1—UJ-5 至少各提供一张 Mermaid 流程图；每张标出 PG、触发角色、对象状态变化、自动/人工边界、成功结果及失败/恢复回路。M4 可有统一主链加四张类型附图；恢复表保留，但应由流程图引用。

### H-04 页面、资产和可点击原型的覆盖关系没有登记且实际不一致

**位置：**[ux-04 §4.2–4.3](./ux-04-pages-and-wireframes.md#42-原型覆盖策略)、[HTML 原型](./prototype/hotspot-monitor-clickable-prototype.html)。

**证据：**原型实际提供了雷达、未来事件、Event、Task Plan、审核、任务中心、效果和异常等交互，但 `ux-04` 未将它登记为正式“交互行为参考”，也未列明每一个 PG 是否覆盖、以何种状态覆盖。它缺少登录/权限、独立 Candidate 处置、监测范围与提醒、配置与字典、独立 Action Task/Receipt、私域/营销/KOL 的完整详情和恢复操作等文档页面。相反，文档高保真表又引用了原型没有路由的若干页面。

**下游影响：**实现团队会不知道以文档、SVG 还是原型为准；原型交互还可能被误读为完整产品验收范围。

**修复：**在 `ux-04` 建立资产登记表：`PG → 线框 → 高保真 → 原型 route/交互 → 覆盖状态 → 权威优先级`。明确“页面规格与状态规则优先于图稿和原型”；给原型每个视图对应 PG/场景 ID，或把未覆盖页面标为“spine-only/待原型化”。

### H-05 交付物审核与 Telegram 审核的操作语义存在歧义

**位置：**[ux-03 §3.1](./ux-03-user-flows.md#31-ux-f01-phase-0-黄金主链)、[ux-05 §5.3、§5.5](./ux-05-interaction-and-states.md#53-execution-deliverable-draft-审核)、[HTML 原型审核页](./prototype/hotspot-monitor-clickable-prototype.html)。

**证据：**流程写为“预检 → Telegram Bot 投递 → 审核结论”；而原型按钮文案为“通过并投递 Telegram 审核”，会让人理解成系统内先“通过”再发送到 Telegram。`ux-05` 又规定快捷结论回写前不生效。三者没有明确 Telegram 是唯一审批表面、并行协作出口，还是系统审核的一个补充入口；也没有定义重复结论、多人相反结论、草稿在 Telegram 审核期间被修改、消息撤回/目标失效的裁决规则。

**下游影响：**审核状态的权威性和可审计性会被实现成两套不同状态机，直接影响是否可创建 Action Task。

**修复：**选择并写死一种模式：建议为“系统审核状态机唯一权威；Telegram 是受控远程审核入口”。规定投递前状态、快捷操作创建何种待同步命令、成功回写的幂等键、冲突结论的仲裁者、草稿版本失效时按钮行为、超时与重投规则。同步修改 UX-F01、审核组件 CP-08/20、PG-07/17 规格与原型文案。

### H-06 结果学习和策略回写缺少可实现的审批与数据缺口交互

**位置：**[ux-03 §3.11](./ux-03-user-flows.md#311-ux-f11-结果学习uj-5)、[ux-04 PG-14](./ux-04-pages-and-wireframes.md#41-页面清单)、[ux-05](./ux-05-interaction-and-states.md)；对照 [PRD FR-21—25](../product-requirements/prd/prd-04-functional-requirements.md#45-m5-效果与学习) 和 [PRD §6.6](../product-requirements/prd/prd-06-business-and-data-rules.md#66-结果关联与最低归因规则)。

**证据：**UX 只说明“缺失/冲突不显示完整结果、建议获批后回写”，没有定义 Outcome 的关联状态、口径冲突处理、数据来源/更新时间展示、策略建议草拟/待批准/已批准/被拒绝/归档状态、批准人和回写影响范围。原型中的“批准并受控回写策略”是单个按钮，无确认或回滚/影响预览。

**下游影响：**无法安全实现 PRD 要求的“仅批准后回写且不得自动覆盖既有规则”，也无法写出结果归因与审计的验收。

**修复：**为 PG-14 增加结果/建议两层规格：Outcome 维度、来源、时间、口径、关联状态、缺口和纠正入口；Strategy Recommendation 的对象状态、适用范围预览、差异确认、批准角色、回写后的审计链接与失败恢复。补一张 UX-F11 流程图。

## Medium

### M-01 通用页面状态是原则，尚未映射到页面和对象状态

**位置：**[ux-05 §5.9](./ux-05-interaction-and-states.md#59-页面基础状态)、[ux-07 §7.3](./ux-07-accessibility-and-validation.md#73-状态覆盖)。

**证据：**`ux-07` 声称 PG-02A—PG-17 都覆盖加载、空、成功、失败、部分成功和权限受限，但未提供“每个页面 × 适用状态 × 触发条件 × 展示/可用操作 × 恢复动作”的矩阵。诸如雷达来源延迟、Evidence 不可访问、Candidate 重复、Event 窗口过期、未来事件改期、任务部分回执、结果口径冲突等高风险状态没有落到具体页面。

**修复：**建立页面状态矩阵。不要强制每页具有不适用状态，但必须写明“不适用”的原因；为高风险/高频状态提供局部图稿或原型场景。

### M-02 响应窗口规则缺少“过期后页面如何变化”的交接细节

**位置：**[ux-05 §5.6](./ux-05-interaction-and-states.md#56-响应窗口与升级)、[ux-06 CP-19](./ux-06-visual-design-and-components.md#63-核心组件)。

**证据：**已说明截止不得晚于窗口、超时升级不得默认通过，但没有定义窗口已过、窗口被缩短/延长、上游 Event Card 更新导致草稿过期时：哪些按钮禁用、哪些对象变为过期、是否允许查看/复制、是否建立新版本、通知谁、任务是否暂停或取消。

**修复：**为 CP-19 和相关 PG 写状态/动作表；将窗口变化的影响对象和动作与 PRD §6.3/§6.4 映射。此规则尤其应覆盖 PG-04、06、07、08、13、15、17。

### M-03 M1/M2 数据可视化只有内容要求，缺少交互、口径和无障碍合同

**位置：**[ux-04 §4.4](./ux-04-pages-and-wireframes.md#44-共同页面框架)、[ux-06 CP-21—24](./ux-06-visual-design-and-components.md#63-核心组件)、[ux-07 §7.1](./ux-07-accessibility-and-validation.md#71-可访问性基线)。

**证据：**雷达榜单、未来事件时间轴、事件监测图、Evidence 抽屉列出了显示字段，但没有确定热度的时间粒度/比较基线、Top 10 并列和无数据规则、图表节点键盘访问/文本替代、筛选的组合和保存行为、来源跳转失败、Evidence 引用打开方式或来源权限失效时的降级。

**修复：**为 CP-21—24 补“输入数据及口径、交互、加载/空/错误、键盘/读屏、导出/深链、权限”子表；确认图表可通过表格或文本摘要完成同一代表任务。

### M-04 组件目录没有足够的行为和状态规范，难以复用

**位置：**[ux-06 §6.3](./ux-06-visual-design-and-components.md#63-核心组件)。

**证据：**24 个组件大多只有一行字段枚举，例如 CP-08、CP-11、CP-17、CP-20、CP-21—24。没有触发方式、可编辑性、校验、确认、禁用、错误、焦点、键盘、异步与权限状态；设计变量也未给出 focus、disabled、overlay、层级和组件变体规则。

**修复：**先为高风险组件建立完整合同：审核卡、Telegram 目标选择、异常卡、响应窗口、审核投递回写、雷达、Event 监测图、Evidence 抽屉。每项至少含输入、输出/事件、状态、可见性、键盘与辅助技术规则、失败恢复；视觉 token 仅补实现必需部分。

### M-05 Four-action 的页面/任务粒度仍不稳定

**位置：**[ux-02 §2.4](./ux-02-information-architecture.md#24-task-plan-与行动类型)、[ux-04 PG-07—13](./ux-04-pages-and-wireframes.md#41-页面清单)、[ux-05 §5.2](./ux-05-interaction-and-states.md#52-类型专属状态)。

**证据：**文档把四类行动描述为统一任务中心的二级视图，但又以 PG-08—12 作为独立页面，并把审核中心作为既可列表也可详情的 `PG-07`。没有给出“类型概览 → 草稿详情 → 审核 → Action Task → Receipt 详情”的固定层级、URL 参数/深链和返回路径。

**修复：**在页面地图和各页规格中固定层级；例如区分 `任务中心总览`、`行动类型列表`、`交付物详情`、`审核详情`、`行动任务详情`、`回执详情`。若采用单页工作区，定义 Tab、主对象 ID 和深链格式，不以视觉图推断。
