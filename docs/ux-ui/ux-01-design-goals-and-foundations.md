# 01 设计目标与基础

## 1.1 体验目标

1. **先看可操作结果。** 首页先回答内容表现、待处理异常、账号任务推进和当前热点；不把复杂研判塞进总览。
2. **趋势、事件与内容严格区分。** 热搜榜回答“什么选题正在火”；热点内容回答“什么具体内容传播有效”；Event 回答“当前运营上下文是什么”。三者不得互相冒充事实。
3. **Event 是下游共同上下文。** Event Card 同时服务内容响应与活动策划；两条链并行，活动建议不阻塞内容任务。
4. **内容以账号为最小单元。** 一个账号响应任务对应一个 Event × 一个承接账号；候选、选择、调整、发布与回填均不跨账号混用。
5. **自动化生成，人工发布。** 系统可创建任务、生成至少三条候选并预检；内容运营在系统内选择/调整，在 X 手动发布并回填 URL 或失败原因。
6. **来源状态诚实可见。** 来源一致、冲突、未知影响允许使用的表达，不把冲突或推断写成确认事实；普通候选可生成，但高风险候选不得绕过审核。
7. **预留能力不伪装已启用。** 热点内容拆解、Content Insight、私域建议显示范围和边界，不用模拟生产数据或占位任务暗示已经可执行。

## 1.2 用户与页面职责

| 用户 | 核心页面 | 主要操作 |
|---|---|---|
| 内容运营 | 热点监测、事件管理、内容发布 | 查看热点与来源上下文；在被分配任务中选择、调整、复制候选；回填 URL/失败原因。 |
| 热点/研究运营 | 热点监测、运营排期、事件管理 | 配置范围；处理聚合、来源、事实和关联异常；维护 Future Event。 |
| 运营负责人 | 运营总览、复盘优化、系统设置 | 看效果和异常；维护规则草稿/发布；确认优化建议。 |
| 活动运营 | 运营排期、事件管理 | 查看活动准备建议；主动启动、选择、调整、导出活动方案。 |

页面对所有授权用户一致；角色只改变可见字段、可执行操作和审批权。账户、工作空间和权限位于顶部全局入口，不作为一级运营页面。

## 1.3 自动化与人工边界

| 系统自动完成 | 人工必须完成 | 禁止系统假装完成 |
|---|---|---|
| 采集 Signal、形成/归并 Candidate Event、地区来源聚合、更新 Event Card、匹配已配置账号、生成候选、运行预检、记录实际耗时 | 校正异常、选择/调整候选、X 平台发布、URL/失败原因回填、启动活动方案、发布规则版本、审核高风险候选 | 自动发 X、Telegram 作为内容主链、自动创建活动、KOL 或私域发送任务、用无数据推定结果 |

## 1.4 关键术语与命名

| 本版正式名称 | UI 名称 | 禁止混用 |
|---|---|---|
| M1 热点发现 | 热点监测 / 运营排期 | 把热搜 Topic 叫 Event |
| M2 事件智能 | 事件管理 | 把 Event Card 叫参与决策卡 |
| M3 活动策划 | Event/排期内的活动准备入口 | Opportunity、Task Plan、活动执行中心 |
| M4 内容响应 | 内容发布 | 通用任务中心、Action Package |
| Account Response Task | 账号响应任务 | Action Task、渠道任务 |

| Content Candidate | 内容候选 | 可直接发布的系统内容 |
| Publication Record | 发布记录 | 传播结果 |
