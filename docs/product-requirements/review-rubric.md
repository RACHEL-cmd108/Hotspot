# PRD Quality Review — 热点运营系统业务可扩展性需求

## Overall verdict

这份文档已经形成了清晰的“三环节可扩展”产品骨架：扩展边界、配置对象、爆款洞察、通用 Skill、渠道适配、版本追溯和业务结果归因能够连成一条主线，作为产品与技术共同讨论的需求基线是合格的。它目前还不是可直接批准进入 UX、架构和故事拆分的完整 PRD：首期范围、关键指标口径、性能与规模边界、权限审批、失败降级及大部分 FR 的可测试结果仍待确定，且多角色操作流程没有通过用户旅程闭合；若直接开工，不同团队会对“配置化”“完成”“有效”和“新渠道只需适配”作出不同解释。

## Decision-readiness — thin

文档在 §2.3 明确了“业务配置”和“技术开发”的原则边界，在 §2.2 排除了首期全平台覆盖与具体技术选型，并在 §13 集中列出待评审项。这些内容让决策者能看见主要问题，但尚未把问题转化为需要谁在何时作出的明确决策。

尤其是首期平台/渠道、最终指标口径、数据降级、自动生效边界、Skill 治理负责人、规模与延迟目标全部仍在 §13 待定。这些事项直接影响方案规模、权限模型、验收数据和首期承诺，属于开工门槛而非普通后续优化。文档也没有呈现主要方案取舍，例如配置自由度与安全控制、统一对象模型与平台特性的保真度、快速实验与统计可信度之间牺牲了什么。

### Findings

- **high** 首期产品边界尚未形成决策（§13“首期正式接入的平台、监测类型和分发渠道范围”）— 文档要求覆盖多种来源与渠道，却未列出 MVP 必须交付的具体组合；无法据此批准预算、排期或验收。*Fix:* 增加“首期承诺 / 后续扩展 / 明确不做”三栏范围表，至少冻结首期监测平台、来源类型、内容形式、账号数量和分发渠道。
- **high** 核心业务指标仍无可执行口径（§9.1、§13）— “新增粉丝”“新增用户”“有效流量”虽有方向性定义，但数据源、基线、归因窗、去重和成功阈值待定，AC-14 因此不能作出通过/失败判断。*Fix:* 为每个最终指标指定公式、数据源、刷新频率、归因窗、基线算法、缺失数据处理、负责人和首期成功阈值。
- **medium** 决策责任与截止条件缺失（§13）— 待评审项没有 owner、决策日期、阻塞的下游阶段或默认方案。*Fix:* 将其改为决策日志表：问题、候选方案、推荐方案、owner、截止日期、阻塞项和决议状态。
- **medium** 关键权衡被原则性表述覆盖（§3、§7.1、§8）— “统一能力”“公共字段”“平台特有字段可以扩展”没有说明统一性与平台特性冲突时的优先级。*Fix:* 增加 3–5 项显式产品决策，记录选择、放弃项与例外机制，例如公共状态机不可破坏、特有能力通过扩展字段/能力声明暴露。

## Substance over theater — adequate

多数内容是针对热点运营系统真实问题写成，而不是模板家具。§4 的配置对象、§5.4 的爆款判定与 Content Insight、§6.3 的 Skill 准入、§7.3 的统一回流和 §8 的异常要求都具备领域特异性；§11 的 NFR 也大多与可扩展平台直接相关。

薄弱点是部分“技术依赖”和 NFR 仍停留在能力名词层面。诸如“可查询、可告警”“单任务可定位恢复”“未授权人员不可修改高风险规则”没有具体角色、阈值或恢复行为，容易在评审时看似全面、实施时却无法约束设计。

### Findings

- **medium** 若干 NFR 仍是不可验收的原则（§11 NFR-002、NFR-005、NFR-006、NFR-007）— “不得阻断”“受权限控制”“可查询、可告警”“无效或冲突配置”没有故障域、角色矩阵、告警时限或校验规则。*Fix:* 为每条 NFR 增加边界和测量方式；无法在 PRD 冻结的数值以 `[NOTE FOR PM]` 标出并纳入 §13。
- **low** 技术依赖与产品需求有重复但缺少能力声明模板（§8）— 表格覆盖了连接、契约、配置、任务、存储等模块，却没有规定每个连接器必须输出哪些可验收的能力元数据。*Fix:* 用一张“连接器能力声明”需求表替换泛化描述，至少含读取、发布、指标、速率限制、鉴权、降级和健康状态。

## Strategic coherence — adequate

文档有明确 thesis：热点运营方法必须频繁试验，因此三环节需要可配置、可组合、可追溯，并最终通过新增粉丝、新增用户和有效流量验证。§1、§2.1、§3、§9 与 §14 基本一致，爆款拆解也被正确定位为监测产物和内容生产输入，而非孤立功能。

问题在于 thesis 尚未转换成优先级和可证伪的首期成功命题。21 条 FR 被平铺呈现，没有 Must/Should/Later 或 MVP 切分；过程指标和最终指标列得较全，但没有反指标触发动作，也没有说明首期究竟要证明“配置效率”“内容效果”还是“渠道复用”的哪一个核心假设。

### Findings

- **high** 无优先级的能力清单无法支撑 MVP 取舍（§10、§12）— FR-001～FR-021 和 AC-01～AC-14 均被默认视为同等承诺，而 §13 又未冻结平台范围；范围一旦受限，没有可依据 thesis 进行削减的规则。*Fix:* 标注 Must/Should/Later，并定义 MVP 是“平台型最小纵切”：至少一个可配置监测平台、一个 Content Insight 复用链路、两个共享流程的分发渠道和一次结果归因实验。
- **medium** 首期验证假设不够聚焦（§2.1、§9.3、总体验收门槛）— “至少以三项之一为主指标完成一次实验”只证明系统能记录实验，不证明可扩展性或业务价值达到预期。*Fix:* 写出 2–3 个可证伪假设及阈值，例如新增同平台来源的业务配置时间、复用组件搭建新生产线的时间、新渠道接入时无需修改的上游模块比例。
- **medium** 护栏指标没有决策规则（§9.2）— 已列出退粉、违规、投诉和成本，但没有阈值、停止条件或优先级，无法约束追求新增指标的副作用。*Fix:* 定义最少一组硬停止阈值与实验淘汰规则，并指定缺失数据时不得自动放量。

## Done-ness clarity — thin

§12 用场景覆盖了三环节和追溯闭环，AC-01、AC-04、AC-06、AC-08、AC-12、AC-13 的行为结果相对明确，是文档最接近“done”的部分。然而，大部分 FR 仍是“支持/可配置/统一/完整”的能力陈述，没有数量、耗时、权限、失败行为、输入边界或可观察输出；验收场景也往往只写“能做”，没有数据集、通过阈值和证据要求。

非功能要求尤其缺少 bounds。§13 已承认配置规模、任务频率、发布延迟和保留周期未定，这意味着性能、可靠性和容量均无法验收。爆款判定与原创性检查虽定义得很细，但没有识别质量目标、人工抽样方法或原创风险阈值。

### Findings

- **high** FR 缺少逐条可测试后果（§10 FR-002～FR-021）— 例如 FR-006 的“可检索、可复用、可版本化”、FR-013 的“所有渠道复用统一能力”、FR-018 的“完整关联链路”都没有判定数据和失败条件。*Fix:* 为每条 FR 至少补一条 Given/When/Then 或明确链接到唯一 AC；列出输出字段、权限、状态和异常结果。
- **high** 非功能指标没有数值边界（§11、§13）— 延迟、吞吐、并发配置数、任务成功率、恢复时间、数据保留、告警时限均未定义，工程无法判断架构是否满足要求。*Fix:* 增加首期容量画像和 SLO 表，包括峰值监测对象数、采集频率、日内容/发布量、P95 延迟、可用性、RTO/RPO、保留周期及成本上限。
- **high** 爆款识别与洞察质量无法判定（§5.4、§9.2、AC-05）— “相对账号基线”“显著超常”“人工认可率”“原创性检查”没有样本窗、精确率/召回率目标、审核量或相似度处置规则。*Fix:* 定义首期基准数据集、基线计算、最低样本、命中率目标、人工抽检流程及原创性阻断/警告阈值。
- **medium** 配置化验收只验证“不改代码”，未验证业务可操作性（§2.3、AC-01～AC-04）— 没有操作角色、完成时长、所需权限、错误校验、审批和回滚时限。*Fix:* 增加“受训业务运营在限定时间内完成”的场景，并规定无效配置提示、预览差异、审批记录与回滚恢复时间。
- **medium** 故障场景覆盖不完整（§8、AC-12）— 仅明确渠道故障隔离；缺少采集限流/凭证过期、模型/Skill 超时、指标回流迟到、配置发布冲突和人工审核滞留。*Fix:* 为三环节各增加至少一个失败、恢复、幂等及降级验收场景。

## Scope honesty — adequate

§2.2 明确了四项非目标，§2.3 清楚区分同平台新增对象与新平台首次接入，避免了“所有变化零开发”的虚假承诺。§13 也诚实列出六类待评审项，整体没有假装所有问题都已解决。

但文档状态是“需求基线（待产品与技术评审）”，正文中没有使用 `[ASSUMPTION]` 或 `[NOTE FOR PM]` 标注推断和阻塞点，也没有假设索引。部分事实性前提——例如平台能获得关注变化、Content Insight 能跨平台归因、渠道能回流后续指标——受到外部 API 能力限制，当前仅在 §8 用一段总括性免责声明处理，容易在下游被当成已承诺能力。

### Findings

- **high** 外部数据可得性假设未逐项暴露（§5.4、§7.3、§9.1）— 粉丝增量、曝光/互动、相对账号历史基线和发布后指标在不同平台可能不可得、延迟或口径不一致；这会直接破坏 AC-05 与 AC-14。*Fix:* 建立平台 × 能力矩阵，逐项标记原生可得、需自建采集、代理指标或不支持，并把缺口转成明确非目标/降级验收。
- **medium** 未决事项没有内联标记与假设回路（全文、§13）— 下游摘取单个 FR 时看不到其依赖的待决口径。*Fix:* 在受影响的 FR/AC/NFR 旁加入 `[ASSUMPTION: …]` 或 `[NOTE FOR PM: …]`，末尾建立 Assumptions Index 并双向对应。
- **low** 非目标尚未覆盖内容合规与自动发布责任边界（§2.2、§6.4、§7.3）— 文档要求品牌、安全和高风险强审，却没有说明系统是否负责法律事实判定、版权许可或平台申诉。*Fix:* 明确首期不承担的合规判断与人工责任，以及自动发布允许的内容/账号风险等级。

## Downstream usability — thin

文档为下游提供了稳定编号的 FR、NFR 和 AC，主链路对象在 §3 中较清楚，FR-001～FR-021、NFR-001～NFR-007、AC-01～AC-14 均连续且唯一。多数章节可以独立引用，且 §4 对配置对象做了集中枚举。

但它是明显的 chain-top 文档，会进入 UX、架构和故事创建，而目前缺少正式 Glossary、FR→AC 的明确映射、角色权限模型和用户旅程。多个关键名词存在重叠或边界未定义，例如“原始信号 / 热点信号 / 事件 / 素材”“生产线 / 内容类型 / 生成方式”“渠道 / 账号”“来源 / 监测源 / 监测任务”；架构和 UX 团队可能据此建出不同对象模型。

### Findings

- **high** 缺少多角色用户旅程与责任闭环（§2“角色边界”、全文）— 标题承诺角色边界，但只描述“业务人员”和“技术”，未覆盖内容审核者、渠道运营、管理员、数据分析者及异常处理者，也没有展示他们如何从配置、试运行、审批到发布和复盘。*Fix:* 增加 4–6 条以具名主人公叙述的关键旅程，至少覆盖新增监测源、洞察复用生产、跨渠道发布、故障恢复和实验复盘，并在旅程中标出权限与交接。
- **high** 缺少领域术语表与对象边界（§3、§4、§5～§7）— 相近名词未定义基数、生命周期和身份规则，无法稳定生成数据模型、接口和故事。*Fix:* 增加 Glossary，定义每个对象的唯一标识、来源、状态、版本语义和关系；明确 Event 与 Content Insight 是否可互转、内容资产与渠道版本的边界。
- **medium** FR 与 AC 未建立可解析对应（§10、§12）— AC 按业务场景组织是合理的，但没有指出覆盖哪些 FR/NFR，若某条 FR 未被验收不易发现。*Fix:* 在每个 AC 增加“覆盖需求 ID”列，或在每条 FR 末尾引用 AC；同时为 NFR 增加专门验证场景。
- **medium** 权限模型不足以支撑 UX 与安全设计（§4、§7.3、§8、NFR-005）— “业务人员”“高风险配置”“未授权人员”均未定义，审核与自动发布谁可操作不清楚。*Fix:* 增加轻量 RBAC 表：角色、可见范围、配置、发布、审批、凭证、回滚和审计权限。
- **low** “Skill”与“Content Insight”仅部分中英混用（§4、§5.4、§6、§10）— 这不是功能问题，但会使 API、界面和故事命名漂移。*Fix:* 在术语表冻结规范名称、中文显示名和复数/版本写法。

## Shape fit — adequate

这不是单一操作者的简单内部工具，而是涉及业务运营、审核/发布、技术接入和分析复盘的多角色平台，并且会向 UX、架构和故事拆分传递。因此采用“目标—对象—三环节能力—依赖—指标—FR/NFR—验收”的能力型 PRD 形状基本合适；把技术选型排除在正文之外也符合 PRD 边界。

不足是文档以平台能力说明为主，低估了多角色、长链路和高风险自动发布对用户旅程与状态流的依赖。同时，§8 已进入架构关注的能力模块，但没有把具体机制移到 addendum，导致产品约束与潜在方案轮廓混在一张表中。

### Findings

- **medium** 多角色平台被写成单纯能力规格（全文，尤其 §2、§4、§12）— 对象列表和功能覆盖充分，但缺少运营人员在真实工作日中的决策、等待、交接、异常和复盘，UX 很难判断信息架构和关键页面。*Fix:* 保留能力规格主干，补充少量负载关键决策的用户旅程和状态转换图，而不是增加独立 persona 清单。
- **low** 技术依赖章节混合产品约束与方案边界（§8）— “异步、幂等、统一输入输出”等是必要约束，但模块化表述可能被误读为已选架构。*Fix:* PRD 仅保留可观察约束与能力契约；模块拆分、存储和编排机制迁入架构 addendum。

## Mechanical notes

- ID 连续性良好：FR-001～FR-021、NFR-001～NFR-007、AC-01～AC-14 均无缺号或重复。
- 文档没有显式 FR→AC、NFR→AC 交叉引用，因此无法机械检查需求覆盖率；AC-07 等场景可推断覆盖多个 FR，但映射不唯一。
- 无 Glossary；“监测源/来源/监测任务”“信号/事件/素材”“生产线/内容类型/生成方式”“渠道/账号”等需要冻结定义。
- 无 `[ASSUMPTION]`、`[NOTE FOR PM]` 或 Assumptions Index；§13 的未决事项无法与受影响需求双向 roundtrip。
- 无用户旅程，因此不存在 UJ ID 或具名主人公；对本多角色、chain-top 平台而言这是实质缺口。
- 标题为“业务可扩展性需求”而非完整产品 PRD，若其用途仅是专项基线，当前覆盖已较全面；若要作为唯一 chain-top PRD，则还需补充用户旅程、权限、范围优先级、数据能力矩阵和量化 SLO。
