# 热点运营系统业务可扩展性需求

> 文档状态：需求基线（待产品与技术评审）  
> 更新日期：2026-08-17  
> 文档目的：定义监测、内容生产、分发三个核心环节的可扩展性要求、技术边界、验收场景和业务指标。本文件定义能力与验收标准，不预设具体技术实现。

## 1. 背景与核心判断

热点运营系统的目标不是完成一次固定的“发现热点 → 生成内容 → 发布”流程，而是持续试验并找到能够稳定带来**新增粉丝、新增用户和有效流量**的运营方法。

热点发现方式、内容形式、内容质量和分发渠道都处在高频变化中。因此，可配置、可组合、可替换、可追溯和可比较是核心验收标准，而非后续优化项。

系统必须支持三个可独立扩展的环节：

1. **监测可扩展**：支持热搜、指定账号、圈层账号、YouTube、搜索及其他小众平台；同一平台首次接入后，新增监测源由业务人员配置，不再重新开发。
2. **内容生产可扩展**：支持多种内容类型、生成方式、语气和可复用 Skill；新增业务组合优先通过配置与复用实现，避免为单个事件或账号创建一次性 Skill。
3. **分发可扩展**：增加新渠道时复用统一的内容适配、审核、排期、发布、状态回流和效果追踪能力，不为每个渠道重做整条流程。

## 2. 目标、非目标与角色边界

### 2.1 产品目标

- 业务人员能够快速创建和调整运营实验，不因常规业务变化等待研发排期。
- 三个环节可以独立变化并自由组合，不形成来源、内容、账号与渠道的硬绑定。
- 每次发布可追溯至监测源、触发规则、内容策略、Skill、账号、渠道和配置版本。
- 系统能够按实验维度比较结果，并以新增粉丝、新增用户和有效流量验证平台价值。

### 2.2 非目标

- 不要求首期接入所有可能的平台和渠道。
- 不要求业务人员在零开发情况下接入协议、鉴权或数据结构完全不同的新平台。
- 不以“生成成功”“发布成功”或单纯曝光量作为平台最终成功标准。
- 不在本文件中规定具体架构、厂商或模型选型。

### 2.3 业务配置与技术开发的边界

| 变化类型 | 默认处理方式 | 示例 |
|---|---|---|
| 已接入平台内新增对象 | 业务配置，不开发 | 新增 X 账号、YouTube 频道、关键词、榜单、搜索式 |
| 使用已有能力创建新组合 | 业务配置，不开发 | 新主题圈、新语气、新账号绑定既有生产线 |
| 调整运营规则 | 业务配置并形成新版本 | 抓取频率、阈值、候选数、审核门槛 |
| 新平台或新渠道首次接入 | 一次性技术接入 | 新增 Reddit 数据源或 Discord 发布适配器 |
| 外部接口不兼容变化 | 技术维护 | API、权限、字段或限流策略变化 |
| 全新基础能力 | 开发后沉淀为通用能力 | 新媒体处理、新模型能力、新审核机制 |

判断原则：如果变化只涉及业务对象、参数、规则或既有能力的组合，就不得要求修改代码或重新部署。

## 3. 总体模型与扩展原则

三环节通过标准业务对象连接：

**监测任务 → 原始信号 → 事件/素材 → 内容任务 → 内容资产/渠道版本 → 分发任务 → 发布结果 → 效果归因**

- **配置与连接器分离**：平台差异由一次性连接能力处理，平台内对象和业务规则由配置处理。
- **内容与渠道分离**：先形成表达目标与核心内容，再按渠道规则生成渠道版本。
- **生产线、Skill、语气、账号分离**：四者可以多对多组合，不为每个组合复制实现。
- **统一生命周期**：不同来源、内容和渠道复用创建、启停、审核、运行、失败、重试、归档等通用状态。
- **配置版本化**：影响结果的配置记录版本、生效时间和操作者，历史结果保留原始口径。
- **全链路关联**：从发现到业务结果使用稳定标识关联，支持按任一实验维度比较。

|---|---|---|---|

## 5. 监测环节可扩展性要求

### 5.1 来源形态

监测模型至少能够表达：

- 热搜、榜单和趋势；
- 指定账号、频道或页面；
- 圈层账号集合、List 或 Community；
- 关键词、搜索式和主题查询；
- YouTube 视频、频道及趋势；
- 新闻、Reddit、Telegram 等小众或垂直平台；
- 日历、官方公告等未来事件源；
- 人工录入、文件导入或外部推送。

不同来源可形成不同用途的对象：热点信号可触发事件；爆款内容可形成内容洞察；历史资料可仅作为生成上下文；未来事件可进入排期。来源接入不等于必须进入同一流程。

### 5.2 平台内新增来源配置化

平台完成首次接入后，业务人员应能自行新增或批量导入账号、频道、关键词、搜索式、榜单和地区；创建主题圈；配置频率、时间窗、优先级和去重；选择仅沉淀素材或允许触发事件；试运行后启用。

新增同类型监测源不得要求修改代码、创建专用脚本或重新部署。

### 5.3 规则可比较、可回滚

排名范围、排名变化、增长速度、跨地区数量、关键词匹配、圈层热度、爆款阈值、事件评分、冷却时间和去重窗口均不得写死。

每次运行记录规则版本、输入快照、命中原因和处理结果。业务人员可比较新旧规则的信号数、有效事件率、误报率、发现提前量和最终业务效果，并恢复旧版本。

## 6. 内容生产环节可扩展性要求

### 6.1 组合模型

一次内容生产由以下对象组合，而非固化成专用 Skill：

**素材/事件 + 上下文包 + 内容类型 + 生成方式 + 通用 Skill + 语气/人设 + 质量规则 + 渠道约束**

例如，“AI 圈层事件 + 历史检索 + 观点评论 + 指定语气 + X 长帖”应组合已有对象得到，而非新建一次性 Skill。

### 6.2 生产线、上下文与内容形式

生产线可包括快讯、深度分析、产品承接、历史关联、数据图表、观点评论、爆款启发、视频脚本、社群讨论和活动预热。内容形式可包括短帖、长帖、Thread、评论、图片文案、视频脚本、社群消息和 Newsletter。

每条生产线声明适用素材、必需/可选上下文、生成步骤、输出类型、可用 Skill、适配渠道、质量门槛、审核要求和效果指标。新增生产线优先引用已有组件。

上下文支持按需组合事件事实、来源证据、产品资料、历史资料、内容洞察、账号和渠道规则；结果可追溯实际使用的资料及版本。

### 6.3 Skill 复用与治理

Skill 应代表跨事件、账号或渠道可复用的稳定能力，例如事实核验、标题生成、结构改写、历史类比、渠道压缩和风险检查。

新增 Skill 必须满足至少一项：现有 Skill 无法通过参数或组合完成；能够跨多个业务对象复用；具有独立、稳定且可测试的输入输出契约。仅改变主题、账号、语气、字数、候选数或渠道时，不得新建 Skill。

Skill 必须有版本、适用范围、依赖、质量样例、负责人和停用策略；升级后历史内容仍可追溯旧版本。

### 6.4 生成与质量策略

业务人员可配置候选数量、自动/人工触发、单次/分步生成、检索增强、重新生成条件、重试、多渠道版本、质量阈值和审核门槛。

质量至少覆盖事实准确、来源可追溯、事件相关、观点清晰、账号风格、渠道适配、原创性、品牌与安全。检查结果及人工修改应回流，供后续比较。

## 7. 分发环节可扩展性要求

### 7.1 新渠道复用通用能力

新增 X、YouTube、Telegram、Discord、Newsletter、官网、博客或私域渠道时，仅新增或配置渠道适配能力，复用：内容接收、渠道版本生成、格式校验、账号选择、排期、审核、发布、幂等、失败重试、状态和效果回流。

不得为新渠道复制独立的内容发现、审批、任务状态和效果追踪流程。

### 7.2 内容、账号与渠道多对多

支持一条生产线对应多个账号、一个账号使用多条生产线、一个内容资产生成多个渠道版本，以及账号停用或超额后切换其他合格账号。

匹配规则可考虑内容类型、主题、受众、人设、渠道限制、剩余额度、重复响应、时间冲突和风险等级。业务人员可配置优先级，并查看选择或排除理由。

### 7.3 发布策略与统一回流

渠道可独立配置人工复制、跳转、定时、API 自动、批量排期、发布前确认和高风险强审。当前 X 可采用人工发布与 URL 回填，但不得成为所有渠道的固定前提。

所有渠道统一回流任务状态、账号、渠道、时间、内容 ID/URL、实际发布版本、失败原因、重试次数和后续指标。渠道特有字段可以扩展，但不得破坏公共字段和统一查询。

## 8. 技术依赖与约束

| 依赖能力 | 支撑要求 | 失效或异常要求 |
|---|---|---|
| 平台连接与鉴权 | API/抓取/Webhook、限流、凭证、健康状态 | 暂停受影响任务并告警，不影响其他连接 |
| 标准对象与能力契约 | 监测输入、内容资产、渠道版本、分发结果公共字段 | 新适配器不改写上下游 |
| 配置与版本管理 | 校验、草稿、预览、生效、审计、回滚 | 无效配置阻止生效，历史保留原版本 |
| 任务编排与状态管理 | 异步、超时、幂等、重试、人工节点 | 单任务可定位恢复，不重复发布 |
| Skill/模板运行 | 统一输入输出、版本、依赖和运行记录 | 失败定位到具体 Skill 与版本 |
| 内容与证据存储 | 保存来源、上下文、草稿、渠道版本及关系 | 内容可回溯事实来源和生成过程 |
| 权限与安全 | 控制配置、凭证、审核和发布 | 未授权人员不可修改高风险规则 |
| 指标采集与归因 | 渠道指标、站点分析、注册和关注变化 | 缺失标记为未知，不得默认为零 |
| 可观测性 | 连接、任务、延迟、失败率、成本和用量 | 区分无信号、未运行和运行失败 |

平台 API、权限、数据粒度和回传能力可能不同。接入评审必须声明支持的监测、发布、指标能力及降级方案，不得用不可获得的数据承诺验收。

## 9. 业务指标与实验闭环

### 9.1 最终价值指标

- **新增粉丝**：约定归因窗口内目标账号净新增粉丝及相对基线增量。
- **新增用户**：由内容或活动带来的有效注册/激活用户，按可识别链接、活动码或约定规则归因。
- **有效流量**：进入目标落地页并满足质量条件的访问，如有效会话、停留、关键页面到达或转化。

三项指标必须按监测方式、内容生产线、内容类型、Skill 版本、语气、账号、渠道和实验版本切分。无法直接归因时，必须声明代理指标、假设和置信度。

### 9.2 过程与护栏指标

- 监测：有效信号率、误报率、发现提前量、事件覆盖率；
- 内容：生成耗时、一次通过率、人工修改率、事实错误率、单条成本；
- 分发：发布成功率、发布延迟、失败恢复时间、重复发布率；
- 传播：曝光、播放、互动率、点击率、分享率；
- 护栏：退粉、负反馈、违规/下架、投诉、审核事故、异常成本。

过程指标用于诊断，不替代最终价值指标。

### 9.3 实验记录

每个实验至少记录假设、唯一主要变量、对照/基线、目标人群、起止时间、配置版本、主指标、护栏指标、观察窗、样本限制和结论。

系统应能回答：哪种发现方式更早且更有效；哪种内容类型、生成方式、Skill 或语气更好；哪个账号与渠道组合更适合某类事件；哪些规则应继续、调整或停止。

## 10. 功能需求

### 10.1 监测

- **FR-001**：业务人员可在已接入平台内新增、批量导入、编辑、复制、分组、启停监测源，无需修改代码或部署。
- **FR-002**：业务人员可配置频率、范围、触发阈值、去重、冷却和事件形成方式。
- **FR-003**：系统支持榜单、账号/频道、圈层、搜索、未来事件和人工导入等来源形态。
- **FR-004**：监测规则支持草稿、预览/试运行、发布、版本比较和回滚。
- **FR-005**：每条信号记录来源、采集时间、规则版本、命中原因和后续结果。

### 10.2 内容生产

- **FR-006**：业务人员可组合素材、上下文、内容类型、生成方式、Skill、语气、质量规则和渠道约束。
- **FR-007**：生产线、Skill、语气、人设、账号和渠道独立管理并支持多对多绑定。
- **FR-008**：新增内容类型或业务组合优先通过配置已有组件实现。
- **FR-009**：Skill 具备明确输入输出、版本、适用范围、依赖、测试样例和运行记录。
- **FR-010**：支持候选数、触发方式、重试、重新生成、多渠道版本和审核策略配置。
- **FR-011**：内容记录上下文、资料来源、配置和 Skill 版本，以及质量检查和人工修改。

### 10.3 分发

- **FR-012**：所有渠道复用统一的内容接收、适配、审核、排期、发布、失败处理和结果回流。
- **FR-013**：业务人员可配置内容、账号和渠道匹配规则，并查看匹配解释。
- **FR-014**：渠道可独立配置人工、定时、自动发布及审核门槛。
- **FR-015**：分发回流统一状态、版本、账号、渠道、时间、内容 ID/URL、错误和效果数据。
- **FR-016**：新增渠道适配器不得要求改写监测与内容生产流程。

### 10.4 实验与度量

- **FR-017**：保存从监测源到业务结果的完整关联链路及各环节配置版本。
- **FR-018**：业务人员可创建实验并配置基线、变量、观察窗、主指标、护栏指标和成功标准。
- **FR-019**：按关键实验维度统计新增粉丝、新增用户和有效流量。
- **FR-020**：规则或口径变更后，历史数据仍按原版本可解释，新旧版本可比较。

## 11. 非功能要求

- **NFR-001 可追溯性**：任一发布内容都能定位来源、规则、上下文、生产线、Skill、账号、渠道和版本。
- **NFR-002 隔离性**：单一来源、Skill 或渠道故障不得阻断其他无依赖链路。
- **NFR-003 幂等性**：任务重试不得造成重复事件、内容任务或发布。
- **NFR-004 可解释性**：展示规则命中、质量拦截和账号/渠道选择的主要原因。
- **NFR-005 权限审计**：凭证、自动发布、审核门槛等高风险配置受权限控制并留痕。
- **NFR-006 可观测性**：任务运行、延迟、错误、重试、调用量和成本可查询、可告警。
- **NFR-007 配置安全**：无效或冲突配置不得直接生效，提供校验与试运行。

## 12. 验收场景

| ID | 场景 | 验收标准 |
|---|---|---|
| AC-01 | 新增同平台监测源 | 新增 10 个 X 账号并组成 AI 主题圈，试运行后启用；不改代码、不部署 |
| AC-02 | 新增 YouTube 任务 | 连接已存在时，业务人员新增频道、关键词和频率，信号带来源与规则版本 |
| AC-03 | 新增小众平台 | 技术只实现一次连接适配；业务人员可自行新增第二批监测对象 |
| AC-04 | 调整触发规则 | 预览命中差异，发布新版本并恢复旧版本；历史命中仍按原版本解释 |
| AC-05 | 复用内容能力 | 不新建 Skill，组合既有历史检索、观点生成、指定语气和长帖模板完成新主题内容 |
| AC-06 | Skill 治理 | 升级后新任务用新版本，历史任务仍展示旧版本和输入输出 |
| AC-07 | 多内容形式 | 同一核心内容生成 X Thread、Newsletter 和 YouTube 脚本，关联同一内容资产 |
| AC-08 | 新增账号 | 第二个快讯账号绑定既有生产线并分担额度，不复制生产流程或 Skill |
| AC-09 | 新增分发渠道 | 首次适配后复用既有审核、排期、状态与重试；监测和生产流程无改动 |
| AC-10 | 渠道故障隔离 | 一个渠道失败并重试，其他渠道继续发布且不重复 |
| AC-11 | 完整追溯 | 从发布 URL 反查来源、规则、上下文、内容、Skill、审核、账号、渠道和实验 |
| AC-12 | 业务价值验证 | 按发现方式、内容类型、Skill/语气、账号和渠道比较三项最终指标及护栏指标 |

总体验收门槛：

- 已接入平台内新增同类对象只需配置；
- 已有组件的新组合只需配置；
- 新平台/渠道只新增边界适配，既有上下游流程保持不变；
- 配置变更可审计、可回滚，实验结果可按原版本解释；
- 至少以新增粉丝、新增用户或有效流量之一为主指标，完成一次端到端实验评估。

## 13. 待评审项

- 首期正式接入的平台、监测类型和分发渠道范围；
- “有效流量”“新增用户”的口径、数据源和归因窗口；
- 各平台可获得的数据粒度及替代指标；
- 哪些配置自动生效，哪些必须审批；
- 通用 Skill 的准入、测试、升级和下线负责人；
- 配置规模、任务频率、发布延迟和数据保留周期目标。

## 14. 一句话定义

热点运营系统的业务可扩展性，是让业务人员在不持续依赖开发的情况下，配置和组合“发现什么、如何生产、向哪里分发”，并用新增粉丝、新增用户和有效流量持续验证每一种组合是否有效。
