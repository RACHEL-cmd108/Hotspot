# 06 业务与数据规则

实体定义、关联和生命周期请参见 [概念领域模型](./prd-05-conceptual-domain-model.md)。本章仅定义这些实体在业务流程中的治理和约束。

## 6.1 共享对象与数据要求

1. 所有后续对象必须能追溯到上一个主链对象；Task Plan 必须关联唯一 Opportunity Card，Review Draft 与 Action Task 必须关联 Task Plan，Opportunity Card 必须关联 Event Card。
2. Event、Opportunity、Task Plan、Review Draft、Action Task、审核、回执、结果和策略建议的关键变更必须记录操作人、时间、原值、新值和原因。
3. 事实真实性、事件热度、增长价值、品牌风险和归因置信度为独立字段，不能相互推定。
4. Source Evidence 至少包含来源、采集/观察时间、可信等级、适用事实及可访问引用；无法复核的输入标记为待确认或不可用。
5. Event Card 的版本仅在事实边界、关键证据、风险、生命周期或窗口发生实质改变时产生；版本不覆盖历史审计记录。

## 6.2 事实、热度与风险治理

1. 官方或一手来源可支持系统自动形成事实；证据冲突、低置信度或高风险事实必须进入例外升级，高风险行动仍需要人工授权。
2. 非官方事实至少需要两个相互独立的可靠来源交叉确认；单一非官方来源保持“待确认”。
3. 观点、预测、传闻和系统推断必须标明性质，不得作为已确认事实进入可发布或高风险行动。
4. 热度可由跨来源讨论、传播速度、跨地区出现和持续时间判断；热度不能替代事实真实性或业务价值。
5. 品牌、法律、平台政策或用户安全的高风险标记必须从 Event Card 传递至 Opportunity Card、Review Draft 和 Action Task。

## 6.3 状态规则

| 对象 | 状态与流转 | 规则 |
|---|---|---|
| Candidate Event | 新建 → 待形成 → 已形成 / 已忽略 / 已合并 | 忽略和合并必须保留原因与原始 Signal。 |
| Event | 待核验 → 监测中 / 待决策 → 已关闭；监测中可再激活 | 证据不足进入监测中；重新活跃、事实更新或窗口变化可再激活。 |
| Opportunity | 待评估 → 优先参与 / 参与 / 观察 / 不参与 | 观察需重新评估时间；不参与记录原因；前两档才可创建行动。 |
| Task Plan | 草拟 → 已选定 → 已撤销 / 已关闭 | 系统建议不能替代人工决定；选定方案必须声明目标、责任人、窗口和风险边界。 |
| Review Draft | 草拟 → 待审核 → 已通过 / 需修改 / 已驳回 | 审核结论必须记录审核者、时间和意见；“需修改”只能经新版本再次审核后通过。 |
| Action Task | 待交接 → 已接收 → 进行中 → 已完成 / 已暂停 / 异常 / 已取消 | 仅从已选定 Task Plan 拆解；外部执行状态以 Task Receipt 为准，越界或高风险变化必须升级。 |
| Strategy Recommendation | 草拟 → 待批准 → 已批准 / 已拒绝 / 已归档 | 已批准建议必须注明回写范围；不得自动覆盖既有规则。 |

## 6.4 权限与决策权

| 业务动作 | 默认角色 | 规则 |
|---|---|---|
| 监测范围、Candidate Event 与 Event 校正 | 热点/研究运营 | 可维护事实和关系，但不具备高风险行动授权权。 |
| 机会价值、资源和参与决策 | 增长负责人、指定业务所有者 | 覆盖系统建议必须记录依据和原因。 |
| 常规低风险草稿审核 | 内容、产品或渠道的指定审核者 | 草稿经事实与风险预检后进入人工审核；审核通过才可作为交接交付物，审核结论须留痕。 |
| 跨团队、产品承接或额外资源投入的行动 | 增长负责人、资源/业务负责人 | 行动责任人提交，获得相应负责人确认后方可向责任团队或外部系统交接。 |
| 高风险行动审核 | 品牌/风控和指定审核者 | 未审核动作不得标记为可交接；系统不得代替外部专业系统发布或执行。 |
| 执行回报、结果和复盘录入 | 行动责任人、数据团队 | 估算、缺失和异常结果必须标注口径。 |
| 共享业务字典管理 | 指定字典管理员 | 修改应评估生效范围；历史记录不被改写。 |

**审批触发与升级规则：**

1. 常规低风险草稿完成系统预检后，必须由指定审核者明确“通过、需修改或驳回”；系统可辅助生成和修订，不得把草稿自动视为发布内容。
2. 涉及跨团队协同、产品承接或额外资源投入的 Action Task，必须由增长负责人或资源/业务负责人确认后方可交接。
3. 涉及品牌、法律、平台政策、用户安全或其他高风险边界的草稿或行动，必须由品牌/风控审核；审批超时后只能升级，不得默认通过。
4. 需要人工确认的 Review Draft 或 Action Task，其确认截止不得晚于对应事件的响应窗口截止；超时应提醒并升级给相应的业务/资源负责人。具体审批时限、预算阈值和提醒频率由各业务线在运营政策或配置中确定。

## 6.5 外部依赖与约束

- 多源外部数据需具备合规接入、可持续成本和可识别的来源状态。
- 专业执行系统可接收已交接 Action Task，并回传进度、异常、完成和结果；它们保有具体制作、发布、上线和活动执行的自主权。回传失败不应删除原任务或已成功数据。
- Telegram 是 Phase 0 首个草稿投递与审核连接器；只能向管理员已批准且 Bot 具备权限的频道、群组或讨论群发送可审核草稿，并记录投递回执；不得直接发布到任何社媒特定账号，也不支持未经同意的批量私信。
- 产品、渠道和业务结果连接依赖统一事件标识、行动标识和预先确认的指标口径。
- 外部数据或回执存在延迟、缺失、冲突时，系统显示数据状态和人工处理入口，而非隐式覆盖。

## 6.6 结果关联与最低归因规则

1. 每个 Outcome 必须关联一个 Action Task，并因此可回溯到相应 Opportunity Card 与根 Event；不能脱离行动单独记录为事件结果。
2. Task Plan 在任务交接前必须选择一个或多个预期结果维度：传播、产品、商业、成本与风险；仅对所选维度追踪结果。
3. 每条 Outcome 至少记录结果类型、来源、时间、指标口径和关联状态。关联状态仅可为“已确认关联”“估算关联”或“数据缺失/冲突”。
4. 缺失数据或口径冲突必须如实标注，不得以其他维度替代，也不得输出精确 ROI 或严格因果归因结论。
5. 结果观察窗口由行动类型或业务配置确定，不在本 PRD 中写死；该窗口应在 Task Plan 选定时对责任人可见。
