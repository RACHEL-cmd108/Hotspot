# 06 业务与数据规则

实体定义、关联和生命周期以 [概念领域模型](./prd-05-conceptual-domain-model.md) 为准。本章定义治理、状态、权限和外部约束。

## 6.1 对象链与模块分流

1. Event 是活动策划和内容响应的共享根上下文；Event Card 是两者的直接输入。M3 活动策划与 M4 内容响应可以并行，任一模块不能阻塞另一模块。
2. 不存在 Opportunity Card、参与/不参与决策或 Task Plan。一个 Event 完成来源聚合并命中生效内容响应规则后，直接创建普通社媒账号响应任务。
3. 每个账号响应任务必须关联唯一 Event 和唯一承接账号/执行主体；社媒候选必须关联唯一任务、账号、Content Skill 版本及可用事实/来源。
4. Content Insight 是具体热点内容的分析对象，不是 Signal、Topic 或 Event。它可关联 Event，或作为独立内容灵感存在；引用它生成草稿时必须保存引用关系，但不得将其传播数据/观点当作事件事实。
5. M3 的活动建议根据 Event Card 形成，仅在用户主动启动后生成三套活动方案草稿；它不构成“是否参与热点”的决定，不自动立项，也不阻塞内容响应。

## 6.2 热点内容与爆款复刻预留规则

1. “热点内容”入口与“热搜榜/重点主题”入口必须可见区分：前者的基本对象未来是具体内容样本，后者的基本对象是趋势项/话题。
2. 当前仅预留 Hot Content Sample 与 Content Insight 的概念对象、入口和复刻边界；不定义首批来源、采集频率、爆款判定、最小拆解字段或自动生成逻辑。
3. 后续启用时，“复刻”只允许借鉴结构、叙事方法、格式、节奏或表达原则，不包括复制原文、视觉素材、未经授权资产、未经核验事实或误导性数据。
4. 在该能力未单独立项前，Content Insight 不触发 Event、账号任务、发布或活动立项，也不作为当前候选生成的输入。

## 6.3 事实、热度与风险治理

1. Phase 0 的合格热搜进入详情后，系统对每个出现地区采集该快照排名前 3 条推文，记录地区、排名、快照时间、原始链接和采集状态；同一 Event 出现在多个地区时，每个出现地区均按此规则采集。
2. 来源聚合用于形成运营上下文，不等于系统对热点作权威事实认证。Event、Fact 和候选必须展示来源一致、冲突或未知状态；观点、预测、传闻和系统推断不得自动写成确认事实。
3. 来源冲突或待确认不会阻断普通候选生成；运营可根据候选、来源状态和账号边界选择、调整或放弃发布。人工后续校正、补充说明或新发布必须新增记录，不得静默改写旧记录。
4. 热度可由排名、讨论速度、跨地区出现、内容互动线索和持续时间描述；热度不能静默改变来源状态、风险判断或内容质量。
5. Event 的热度观察只提供信息和提醒。窗口、关闭或再激活必须由生效规则或有依据的人工操作改变，并保留原因。
6. 涉及平台政策、明确禁用表达、用户安全或其他高风险边界的标记必须传递至账号任务和候选。高风险候选不得绕过适用的人工审核；系统不得自动向社媒账号发布。
7. 系统可在达到生效高置信度阈值（初始为 `0.95`）并保留依据时自动合并 Event；阈值属于受版本管理的配置，变更只影响后续归并。自动拆分不得执行，只能提出建议。自动合并后，系统比较已生成候选所依赖的关键事实、风险和时间窗口：均未变化则候选继续可用；任一变化则候选标记“需复核”并暂停发布。已回填发布记录只保留历史与复核标记，不回改。

## 6.4 Phase 0 触发、响应与时效

1. X 热搜按小时计划采集。每次成功采集记录快照时间；它用于计算实际采集、聚合、生成、选择和回填耗时，不构成固定分钟级交付 SLA。
2. 重点领域中，已配置关键词进入热搜即为合格触发；普通主题以首次观察排名 1—5，或相邻两次成功小时快照排名上升至少 10 位为合格触发。关键词和门槛必须属于生效 Monitoring Scope。
3. 合格热搜进入详情后，系统采集每个出现地区快照前三条推文并形成来源聚合。每条来源必须保留地区、排名、快照时间、原始链接和采集状态；采集不足三条时保留实际数量和异常原因。
4. 完成来源聚合且命中普通内容响应规则的 Event，系统对三个预配置 Predx X 账号逐一匹配，每个账号创建至多一个账号响应任务。账号或 Skill 不可用时，仅该账号任务进入异常，不得伪造候选或创建替代任务；其他可用账号照常继续。
5. 系统为正常任务生成至少 3 条账号专属候选并完成适用规则预检，使候选可在系统工作台查看、复制、选择和调整。运营在 X 手动发布后，在同一任务回填实际链接或失败原因；不使用 Telegram 作为当前链路入口。

## 6.5 Future Event 与活动策划规则

1. Future Event 的自动窗口、授权用户手动提前启动和实时 Signal 匹配可以并行发生，并汇入同一 Event/Event Card；后续触发更新上下文，不重复创建既有账号任务。
2. 活动准备推荐至少可引用 Event Card 的确认度、受众匹配、时间窗口、目标价值、风险、资源可行性及已批准历史经验；首版优先针对关联 Future Event 的 Event。
3. 用户不点击“生成活动方案”时不得生成活动方案草稿。活动方案必须标注事件确认度、假设和外部执行前提。
4. 每套活动方案至少包含目标、受众、窗口、传播主题、机制/玩法、资源、风险边界与外部执行前提。可写入 KOL 扩散资源建议，但不得产生 KOL 人选、触达、合作或回执记录。
5. 私域当前不生成交付物或任务；未来仅可将已核验 Event/Content Insight 转化为话题讨论建议，发送与互动不属于本系统。

## 6.6 状态规则

| 对象 | 状态与流转 | 规则 |
|---|---|---|
| Candidate Event | 新建 → 待核验 → 已形成 / 已忽略 / 已合并 | 忽略、合并和拆分保留原因与原始 Signal。 |
| Event | 待聚合 → 响应中 / 观察中 → 已关闭；可再激活 | 普通内容响应只在地区来源聚合与响应规则均满足后创建；来源冲突可见但不阻断普通候选生成；活动策划不改变内容响应资格。 |
| Content Insight | 已采集 → 已分析 → 可引用 / 已归档 | 归档不删除历史引用；发现来源、授权或分析错误时标记限制，不静默修改已引用草稿。 |
| Account Response Task | 待生成 → 生成中 → 待选择 → 待发布/待回填 → 已完成 / 已暂停 / 异常 / 已取消 | 创建时绑定唯一 Event 和唯一 Predx X 承接账号。每个合格 Event 对三个预配置账号分别有 0 或 1 个任务；候选/预检完成才可待选择；选择后在 X 手动发布并回填 URL/终止原因才可关闭。 |
| Content Candidate | 已生成 → 预检完成 → 已选择 / 需修改 / 已放弃 | 只绑定一个账号任务；每条候选保留来源状态、账号/Skill 和洞察引用。 |
| Publication Record | 待回填 → 已发布 / 发布失败 | 运营手动发布后回填实际 URL；失败原因不被推定为已发布。 |
| Campaign Case / Campaign Proposal | 已形成 → 待运营决定 → 已启动/已忽略/已过期；方案可生成/调整/导出 | 用户不点击不生成活动方案；方案不代表外部执行完成。 |
| Optimisation Proposal | 草拟 → 待批准 → 已批准 / 已拒绝 / 已归档 | 仅获批建议可在明确范围内更新共享规则；不能改写历史对象。 |

## 6.7 权限与外部约束

| 业务动作 | 默认角色 | 规则 |
|---|---|---|
| 热点/内容发现、范围和触发规则维护 | 热点/研究运营、授权运营负责人 | 修改先保存草稿；发布前显示影响对象与版本差异。 |
| 事件、事实与证据校正 | 热点/研究运营 | 可维护来源聚合与状态上下文，不可绕过适用高风险内容门禁。 |
| 爆款拆解与洞察引用 | 内容运营、授权研究运营 | 可创建/引用洞察，但必须保留原内容来源和复刻边界。 |
| 普通候选选择、调整、发布 | 内容运营 | 仅在被分配账号任务内操作；人工发布后回填 URL 或失败原因。 |
| 高风险内容审核 | 品牌/风控及指定审核者 | 只能明确通过、需修改或驳回；超时只升级，绝不默认通过。 |
| 活动方案启动与选择 | 活动运营、运营负责人 | 推荐后由人点击启动；外部执行不由本系统代替。 |
| KOL / 私域发送 | 不适用 | 系统无 KOL 工作流；私域发送尚未在范围内。 |

- 系统工作台是 Event、Content Insight、候选、任务、候选复制、选择、规则版本与发布回填的权威操作面；Phase 0 不使用 Telegram 作为投递、审核或离线分流入口。
- 运营在 X 平台手动发布；系统不得自动发布至任何社媒特定账号，也不得形成脱离系统审计的独立任务状态。
- 热点内容样本的使用受来源平台条款、授权和内部合规约束；系统只提供引用/拆解关系，不声明内容资产权利。
- 活动方案交接记录不代表外部团队已立项或执行；外部信息不得覆盖原方案版本。
