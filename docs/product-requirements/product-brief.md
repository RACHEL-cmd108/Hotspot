## 2. 执行摘要

### 2.1 产品一句话定义

Hotspot Monitor 是一个事件驱动的增长智能与运营平台，帮助企业发现重要事件、判断增长机会，并将外部变化转化为可执行、可衡量、可复用的增长结果。

### 2.2 产品背景

企业增长越来越依赖外部世界变化：

- 社会热点
- 体育赛事
- 行业事件
- 市场变化
- 用户讨论
- 社区趋势

这些事件能够快速聚集用户注意力，并产生潜在增长机会。

但目前企业通常依靠：

- 人工搜索
- 个人经验判断
- 临时团队协作
- 事后复盘

导致热点运营难以规模化。

Hotspot Monitor 希望建立一套标准化能力：将外部世界正在发生的事件，转化为企业可执行、可衡量、可复用的增长机会。

### 2.3 产品定位

Hotspot Monitor 是一个独立产品，不属于任何单一业务产品。

产品关系：

```text
Company Growth
└── Hotspot Monitor
    ├── Phase 1 → Predx
    └── Future  → Other Products
```

**第一阶段**

Hotspot Monitor 服务 Predx 产品增长。

目标是通过 Predx 真实业务场景验证：事件驱动增长闭环是否能够提升产品增长效率。

**长期方向**

Hotspot Monitor 将成为公司级增长基础设施，支持不同产品、不同市场和不同增长场景。

## 3. 问题与依据

### 3.1 核心问题

#### 问题一：增长团队缺少系统化热点发现能力

现实世界的信息来源高度分散，包括社交平台、新闻媒体、热榜、社区、预测市场、行业日历和产品内部数据。

当前主要依靠人工搜索、筛选、判断和分享，导致发现速度依赖个人能力、重要机会容易遗漏，也无法形成组织能力。

#### 问题二：热点缺少系统化的判断方式

大量热点拥有高关注度，但不一定具备业务价值。

团队需要判断热点是否与产品相关、是否匹配目标用户、是否具备参与资格、是否有产品承接路径，以及是否值得投入资源。目前缺少系统化判断方式。

#### 问题三：事件、信息和业务行动之间缺少连接

现实世界事件会产生新闻、社交讨论、视频、市场变化和用户行为变化，但目前这些信息通常被孤立处理。

缺少完整闭环：

`事件理解 → 增长判断 → 行动执行 → 结果学习`

#### 问题四：增长执行缺少持续学习能力

传统流程是：

`发现热点 → 制作内容 → 发布 → 查看互动`

这一流程只能看到表面结果，无法回答为什么成功、为什么失败、哪类事件值得投入、哪种渠道有效、哪种产品承接有效，导致经验无法沉淀。

### 3.2 当前解决方式与现状成本

当前主要依靠内容运营人工查看 X、新闻与社区信息，手工核对事实，再临时组织内容。

- **人力成本：**重复浏览、筛选、核对和改写；
- **时间成本：**突发热点窗口短，发现和判断延迟会降低内容时效；
- **判断成本：**不同运营人员采用标准不一致；
- **风险成本：**热搜词不等于已确认事实，未经核验容易产生错误表述；
- **学习成本：**缺少统一记录，成功和失败经验难以复用。

当前人工流程的具体耗时、采用率和返工率尚未形成稳定基线，需在 Phase 0 首周记录。

### 3.3 用户、业务和研究证据

当前 Hotspot Monitor 处于产品定义与 Phase 0 验证准备阶段。现有证据主要来自目标用户工作方式分析、内部业务流程观察、行业趋势研究和工程 POC；尚未取得大规模外部用户数据。

#### 3.3.1 用户证据

第一优先用户为内容运营。在突发热点响应中，内容运营需要从分散信息中完成热点发现、事实核验、价值判断、内容生产和人工审核。当前观察到的主要问题包括：

- 信息来源分散，需要大量人工筛选；
- 需要判断什么是真正重要的事件、什么与业务相关、什么值得投入；
- 事实、内容方向、风险边界和审核意见缺少统一连接方式；
- 成功和失败经验难以持续沉淀。

上述内容目前属于工作流程观察，尚需在 Phase 0 通过用户访谈和实际使用记录验证。需要补充的数据包括：当前单次热点响应耗时、候选热点采用率、草稿可用率，以及人工核验和修改的主要原因。

#### 3.3.2 业务证据

企业增长活动天然依赖体育赛事、行业事件、市场变化和社交热点等外部事件。这些事件具有用户关注集中、时间窗口短和增长机会明显的特征。Hotspot Monitor 要验证的业务价值，是能否将已经存在、但高度依赖个人经验的增长行为，转化为可复制的系统能力。

2026-08-04 的本地 X 快照覆盖 Worldwide、美国、英国、日本和韩国五个地区，共获取 150 个原始趋势位，其中 144 个成功补充代表性推文，覆盖率为 96%；最终形成 8 个候选事件簇和 7 个完整 Event Card。

这一结果证明数据链路能够运行，但只代表单次本地快照，尚不能证明长期稳定性、内容业务价值或真实运营效率提升。Phase 0 还需记录热点内容发布后的传播结果和产品结果。

#### 3.3.3 研究证据

当前行业研究得出以下方向性判断：

- 企业增长正从固定计划和长周期活动，扩展到对实时信息和外部变化的快速响应；
- 用户注意力越来越围绕热点事件、社区话题、实时新闻和市场变化形成；
- AI 降低了信息聚合、内容理解、事件分类和趋势分析的成本；
- 社交监听、品牌监测、风险预警和新闻情报类产品，已经验证企业对“更早发现变化、更快理解变化”的需求。

Hotspot Monitor 在现有情报类能力上进一步验证：`事件 → 增长机会 → 产品行动 → 结果学习`。

工程 POC 已完成内容生成与 X 数据适配相关的 9 个单元测试，证明原型行为符合当前代码规则；该结果不等于生产环境已经就绪，也不能替代用户和业务验证。

## 4. 目标用户与场景

### 4.1 主要用户

#### 用户1：增长负责人

**核心任务：**发现高价值增长机会，协调资源投入。

**关注：**机会价值、投入产出和增长结果。

#### 用户2：热点运营／研究运营

**核心任务：**发现和理解外部事件。

**关注：**信号发现、事实确认和事件变化。

#### 用户3（第一优先用户）：内容运营

**核心任务：**围绕事件快速生产内容。

**关注：**事实基础、内容方向和风险边界。

**首版预期结果：**在不降低事实准确性和人工审核要求的前提下，缩短从热点出现到形成可审核草稿的时间。

#### 用户4：产品运营

**核心任务：**连接热点和产品增长。

**关注：**产品承接、用户路径和转化结果。

#### 用户5：数据团队

**核心任务：**分析增长结果。

**关注：**数据追踪、效果分析和经验沉淀。

### 4.2 关键使用场景

#### 场景一（第一优先场景）：突发热点快速响应

事件突然发生时，团队需要快速判断是否真实、是否重要、是否值得行动。

Hotspot Monitor 帮助完成：`发现 → 理解 → 判断 → 行动`。

**首版范围：**获取 X 平台五个目标地区各前 30 的热搜，补充代表性推文，识别事件并整理已确认事实，输出承接建议和待审核草稿，最终由内容运营人工核验并决定是否发布。

#### 场景二：未来事件提前准备

对于体育赛事、行业节点和产品事件，团队提前准备内容、产品承接和增长动作，从被动响应转变为主动准备。

#### 场景三：判断热点是否值得投入

面对大量热点，帮助团队判断业务相关性、用户价值、时间窗口和风险，减少无效追热点。

#### 场景四：热点连接产品增长

将事件关注转化为内容触达、产品访问、用户注册和产品参与。

#### 场景五：增长行动复盘

活动结束后分析哪些事件有效、哪些判断正确、哪些动作值得复制，并形成增长资产。

### 4.3 用户目标与预期结果

| 用户 | 目标 | 预期结果 |
|---|---|---|
| 增长负责人 | 发现增长机会 | 提升增长投入效率 |
| 热点运营 | 快速理解事件 | 降低人工筛选成本 |
| **内容运营（第一优先）** | **快速响应热点** | **提升内容质量和速度** |
| 产品运营 | 连接事件与产品 | 提升产品转化 |
| 数据团队 | 分析增长结果 | 形成增长模型 |

## 5. 产品方案与价值

### 5.1 产品方案概述

Hotspot Monitor 首版建立四层能力：

`X趋势发现 → 事件与事实理解 → 内容承接判断 → 草稿生成、人工审核与结果记录`

### 5.2 核心价值主张

1. **覆盖更稳定：**用固定地区、固定榜单范围替代个人随机浏览；
2. **判断更一致：**用统一评分维度辅助判断，而不是只看热搜排名；
3. **响应更快：**把趋势、代表性推文、事实和草稿放入同一条工作链路；
4. **风险更可控：**草稿只使用输入中的已确认事实和来源，生产发布仍由人最终决定；
5. **经验可沉淀：**记录承接、驳回和修改原因，为后续优化评分与内容策略提供数据。

### 5.3 与替代方案的差异

| 方案 | 能解决什么 | 主要不足 | Hotspot Monitor 的补充价值 |
|---|---|---|---|
| 直接浏览 X 热搜 | 了解正在流行的话题 | 多地区切换、核验和记录成本高 | 统一采集五个地区并保留历史 |
| 社交监听工具 | 关键词和品牌监测 | 不直接形成内容承接判断 | 连接热点评分和内容运营动作 |
| 通用内容生成工具 | 生成文案 | 容易缺少来源和事实边界 | 使用结构化事件输入并执行质量检查 |
| 人工编辑流程 | 判断灵活、质量可控 | 速度和标准依赖个人 | 保留人工决策，同时减少重复收集与整理 |

## 6. 首版范围

### 6.1 包含范围

- X 平台 Worldwide、美国、英国、日本、韩国五个地区；
- 每地区热搜榜前 30；
- 热搜标题、排名、查询词、分类和代表性推文；
- 快照保存与排名历史；
- 趋势去重、候选事件聚类和 Event Card；
- 来源可靠性、时效、传播速度和受众适配评分；
- 拒绝、观察、承接和优先承接建议；
- 三类 X 内容草稿；
- 字数、禁用表述、异常数字、来源链接和版本相似度检查；
- 人工审核及采用、驳回、修改原因记录；
- 以 Predx 内容运营流程作为首个验证环境。

### 6.2 非范围

- X 以外平台的数据接入；
- 自动发布；
- 无人工确认的事实判断或高风险内容决策；
- 完整营销自动化；
- 精确自然传播归因；
- 首版同时服务所有增长角色和业务线；
- 将 TrendRadar 直接认定为长期生产数据源；
- 在未验证前承诺多语言生成质量和生产级稳定性。

## 7. 目标与成功指标

### 7.1 产品目标

验证 Hotspot Monitor 是否能帮助内容运营在突发热点场景中，更快、更稳定地形成事实有据、风险可控的待审核内容，同时留下可用于持续优化的运营数据。

### 7.2 当前可确认的基线

| 指标 | 当前基线 | 说明 |
|---|---:|---|
| 单次趋势采集规模 | 150 | 五地区各 30 |
| 代表性推文覆盖率 | 96% | 单次本地快照，144/150 |
| 原型测试通过率 | 100% | 9/9 单元测试，仅代表当前代码规则 |
| 事件窗口内完成率 | 待采集 | Phase 0 按事件记录 |
| 候选采用率 | 待采集 | 需记录内容运营决策 |
| 草稿可用率 | 待采集 | 按候选事件计算，多个草稿中至少一个可用即计为可用 |

### 7.3 MVP 目标值

| 指标 | 定义 | 候选目标 | 衡量方式 |
|---|---|---:|---|
| 趋势采集完整率 | 实际获得趋势数 / 计划趋势数 | ≥ 95% | 每次采集日志 |
| 代表性推文覆盖率 | 获得代表性推文的趋势数 / 趋势总数 | ≥ 90% | X 快照 |
| 事件窗口内完成率 | 在该事件预先设定的有效响应窗口内形成可审核草稿的候选事件占比 | Phase 0 建立基线 | 记录事件进入系统时间、事件窗口和草稿完成时间 |
| 候选处置完成率 | 在规定时间内形成明确处置结论的候选占比 | ≥ 90% | 任务状态记录 |
| 草稿可用率 | 至少有一个生成草稿被内容运营判定为可用的候选事件数 / 已生成草稿的候选事件总数 | ≥ 60% | 按候选事件记录是否存在可用草稿 |
| 事实/来源质量通过率 | 未出现无来源事实、输入外数字或禁用表述的草稿占比 | 100% | 自动检查加人工抽检 |
| 复盘记录完成率 | 已发布或已关闭任务中完成结果记录的比例 | ≥ 90% | 任务与复盘记录 |

上述指标定义和目标值已确认为 Phase 0 的验证标准。Phase 0 连续验证两周，最少覆盖 30 个进入处理流程的候选热点。事件窗口内完成率首轮用于建立基线，不设统一百分比门槛。

## 8. 假设、依赖与风险

### 8.1 关键假设

- X 五地区热搜前 30 能提供足够的突发热点候选；
- 代表性推文能够补充热搜词的最低事实上下文；
- 内容运营愿意在统一工作流中记录采用、驳回和修改原因；
- 统一评分维度能够提高判断一致性；
- 草稿生成能够节省时间，同时不降低事实准确性。

### 8.2 外部依赖

- `twitterapi.io` 的趋势和搜索接口可用性、额度与返回质量；
- X 的地区 WOEID、趋势排序和搜索结果稳定性；
- TrendRadar 适配层、数据库和排名历史；
- 内容模型服务；
- 内容运营人工核验与审核；
- 账号定位、禁用表达和风控规则。

### 8.3 主要风险

| 风险 | 影响 | 当前应对 | 仍需补充 |
|---|---|---|---|
| 热搜词不是事实 | 可能产生错误或误导内容 | 补充代表性推文，草稿必须保留来源 | 定义可接受来源等级和核验规则 |
| 地区趋势重复或语义不同 | 重复劳动或错误聚类 | 去重与事件聚类 | 多语言人工样本评估 |
| API失败或覆盖不足 | 候选缺失、响应延迟 | 单项失败不阻断全部采集 | 重试、监控和降级门槛 |
| 自动评分不符合编辑判断 | 错过机会或产生低质候选 | 人工最终决定 | 记录分歧并校准权重 |
| 草稿事实或表达风险 | 品牌和合规风险 | 输入约束、质量检查、人工审核 | 风险分级与升级机制 |
| 原型被误认为生产系统 | 范围和可靠性预期失真 | 明确 POC 与生产边界 | 生产就绪门禁 |

#### 事实来源与热度验证的当前原则

- 官方或一手来源可以单独支持事实，但发布前仍需人工核验；
- 非官方信息原则上至少需要两个相互独立的可靠来源交叉确认；
- 只有单一非官方来源时，标记为“待确认”，不得写入可发布草稿；
- 观点、预测和传闻必须明确标注其性质，不得表述为已确认事实；
- 通过跨来源讨论量、传播速度、跨地区出现和热搜持续时间验证事件热度；
- 热度验证只用于判断是否值得响应，不能代替事实真实性验证；
- 特殊情况由 Rachel 决定是否继续处理，但不得跳过发布前人工审核。

#### 响应时间口径

不为所有事件设定统一固定时长。候选事件进入处理流程时，根据事件类型、传播速度和预计热度持续时间，设定该事件的有效响应窗口。从事件进入系统开始计时，到形成至少一个可审核草稿结束，并判断是否在该事件的有效窗口内完成。
