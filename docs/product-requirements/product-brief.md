# Hotspot Monitor Product Brief

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品名称 | Hotspot Monitor |
| 中文名称 | 热点内容运营系统 |
| 产品定位 | 帮助运营人员发现热点与热点内容、形成事件上下文，并更快产出账号专属内容的运营系统。 |
| 首个验证环境 | Predx 内容运营的 X 突发热点响应。 |
| 第一优先用户 | 内容运营。 |
| 当前权威输入 | 产品模块架构图 v3 与概念实体关系图 v12；本 Brief 为与 PRD v2.10 对齐的中间草案。 |

## 2. 一句话定义与产品主张

Hotspot Monitor 将实时热搜、Future Event 和正在流行的具体内容组织为可追溯的 Event 上下文，帮助内容运营更快得到可选、可调整、账号专属的内容候选，并从爆款内容中沉淀可复用的灵感。

产品首先解决两件事：

1. **更快响应。** 热点进入关注范围后，系统自动形成事件上下文并生成内容候选，减少人工在榜单、原帖、资料和写作工具之间切换。
2. **更好生产。** 系统不仅告诉运营“什么选题火”，也逐步解释“什么具体内容火、为何火、哪些结构可借鉴”，为内容生产提供灵感而不是照抄素材。

## 3. 要解决的问题

### 3.1 热点发现与内容灵感分散

运营人员既要知道哪些热搜话题正在上升，也要理解哪些具体内容正在被传播。前者解决选题，后者提供写作灵感；两者当前都依赖人工搜索、截图和经验判断。

### 3.2 热点到内容候选的链路过慢

热搜出现后，运营需要自行打开详情、阅读代表性内容、整理上下文、判断账号口径和起草文案。即使不要求系统对事实作权威判断，这些重复动作仍会错失窗口或消耗创作精力。

### 3.3 具体内容的有效结构没有沉淀

爆款内容常包含可借鉴的 Hook、叙事结构、表达方式、节奏或内容形态，但这些经验通常停留在个人观察，无法被后续账号内容稳定使用。

### 3.4 发布结果没有回到下一次运营

若不关联 Event、账号、候选、发布链接和基础表现，团队无法区分“发现得更早”“写得更合适”或“只是偶然表现好”，也无法改进规则与 Content Skill。

## 4. 用户与关键场景

| 用户 | 核心任务 | 预期结果 |
|---|---|---|
| 内容运营（第一优先） | 查看热点上下文，在账号候选中选择、调整、手动发布并回填链接。 | 更快得到可用内容，不从零起草。 |
| 热点/研究运营 | 维护监测范围、查看来源与聚合结果、校正异常。 | 重点热点稳定进入响应链，来源差异可追溯。 |
| 运营负责人 | 维护规则、账号/Skill、复盘结果。 | 持续改善发现、生成与内容表现。 |
| 活动运营 | 对 Future Event 选择是否启动活动方案草拟。 | 获得可比较的方案草稿，不承担活动执行。 |

关键场景包括：

1. **突发热点内容响应。** 合格热搜自动形成 Event；上下文聚合后，三个预配置 Predx X 账号各自生成账号专属内容候选。
2. **Future Event 预热。** 运营可依据排期窗口、手动提前启动或实时信号匹配进入同一 Event，并沿用内容响应链。
3. **热点内容与爆款拆解（预留）。** 保留独立入口、对象和边界，待后续单独定义来源与口径后再启用。
4. **Future Event 的活动准备。** 系统给出活动准备建议；用户主动启动后生成三套活动方案草稿并导出/交接。

## 5. 产品能力结构与边界

完整产品的能力结构以[产品模块架构图 v3](./prd/assets/hotspot-monitor-product-architecture-v3.svg)为权威来源，概念对象以[概念实体关系图 v12](./prd/assets/hotspot-monitor-conceptual-domain-model-v12.svg)为准。

| 模块 | 核心问题 | 主要产出 |
|---|---|---|
| M1 热点发现 | 什么选题火、哪些 Future Event 值得准备？为热点内容/爆款拆解预留入口。 | Signal、Future Event、Candidate Event；预留 Content Insight |
| M2 事件智能 | 这些信号是否属于同一 Event？来源、冲突、热度与窗口是什么？ | Event、Fact、Evidence、Event Card |
| M3 活动策划 | 是否建议为 Event 做活动准备，以及有哪些方案选择？ | Marketing Recommendation、Campaign Proposal Draft |
| M4 内容响应 | 每个 Predx 承接账号此刻应如何获得和处理内容候选？ | Account Response Task、Content Candidate、发布链接回填 |
| M5 效果与学习 | 哪些响应和内容更有效，下一次改什么？ | Performance Result、Evaluation Report、Optimisation Proposal |

Event Card 是 M3 与 M4 的共同上下文；活动策划与内容响应可以并行，活动不构成内容响应门禁。

明确不在当前系统范围内：Opportunity Card、是否参与热点决策、Task Plan、KOL 筛选/触达/合作工作流、私域触达和发送、活动立项与执行、自动向社媒账号发布。

## 6. Phase 0 验证范围

Phase 0 不是完整产品的缩写，而是在 Predx 场景验证最短内容响应闭环。

### 6.1 进入与来源聚合规则

- X 热搜按小时采集；重点领域关键词进入热搜即触发，普通主题首次进入排名前 5，或相邻成功小时快照上升至少 10 位时触发。
- 合格趋势项进入热搜详情后，系统采集该地区对应快照下排名前 3 条推文作为 Evidence。
- 若同一 Event 同时出现在多个地区榜单，系统对每个出现地区各采集排名前 3 条推文，并按地区保留来源、快照时间和排名上下文。
- 系统根据上述来源形成 Event 与 Event Card。来源一致、冲突或未知均须可见；冲突不阻断候选生成，也不把任何一方自动表述为确认事实。

### 6.2 内容响应闭环

`合格热搜触发 → 各地区前三条 Evidence 聚合 → Event / Event Card → 三个预配置 Predx X 账号分别创建响应任务 → 每个可用账号至少 3 条账号专属候选 → 运营在系统工作台选择、复制或调整 → 运营在 X 手动发布 → 系统回填实际 URL 与结果。`

- Phase 0 配置三个 Predx X 承接账号及其 Content Skill。每个合格 Event 对每个可用账号创建至多一个任务；账号或其 Content Skill 不可用时，仅该账号任务标记为异常，不创建替代任务，也不阻塞其他可用账号。
- 每个正常账号任务至少生成 3 条账号专属候选，并保存所用 Event、来源、账号和 Skill 版本。
- 系统工作台是候选选择、复制、调整、发布链接/失败原因回填的唯一操作面；运营在 X 平台手动发布，系统不直接代发。
- 当前不使用 Telegram 作为投递、审核或离线分流入口。
- 不为生成、选择、发布或回填设定固定分钟级 SLA；Phase 0 记录各阶段实际耗时，用于建立后续性能与运营基线。

### 6.3 Phase 0 非范围

- 热点内容入口和 Content Insight 的正式数据源、爆款判定、最小拆解字段与自动注入生成；当前仅预留入口与概念边界；
- 活动策划、私域话题建议、KOL 能力；
- X 之外的平台接入、超过三个账号的容量编排、自动社媒发布；
- 将来源聚合当作权威事实认证，或对争议信息作自动最终裁决。

## 7. 成功标准

| 类别 | 指标方向 | 说明 |
|---|---|---|
| 发现与聚合 | 合格热搜捕获率、每地区前三条 Evidence 完整率、跨地区来源保留率。 | 验证输入是否稳定进入 Event。 |
| 候选供给 | 已创建账号任务中具备至少 3 条账号专属候选的比例。 | 验证系统是否减少从零起草。 |
| 人工闭环 | 候选被选择/调整后手动发布并回填 URL 的比例及原因。 | 验证内容运营是否愿意采用。 |
| 实际耗时 | 采集、聚合、生成、选择、发布回填的实际耗时分布。 | 建立基线，不以当前固定 SLA 判断通过。 |
| 内容质量与学习 | 候选采用、账号基础表现、Content Insight 采用和规则优化复用。 | 验证“更好生产”的长期价值。 |

反向指标：系统自动向 X 发帖数为 0；没有来源链接或来源状态的候选数为 0；候选跨账号复用数为 0；来源冲突被静默隐藏的 Event 数为 0。

## 8. 假设、风险与下一步

- X 热搜详情中的前三条推文能够提供足以形成初始运营上下文的代表性样本；跨地区出现时，地区分别保留能降低信息丢失。
- 来源聚合不等于事实认证。运营发布前仍可调整表达；来源冲突、未知和后续变更必须保留在 Event 中，便于修订或补充说明。
- 热点内容拆解是否真正提高账号表现，需在后续以可比样本验证。
- Future Event 活动策划是否仅限 Future Event，以及结果观察窗口/比较口径，仍需在相应模块实施前确定。

**当前结论：**产品方向已收敛为“热点发现与内容生产支持”，而不是全渠道机会决策与行动编排。Phase 0 可据此验证三个预配置账号的来源聚合、内容候选供给和人工发布回填闭环；本 Brief 在 PRD 与 v12 概念图完成一致性校验后再升级为正式基线。
