# 热点监控产品阶段汇报

> 汇报日期：2026-08-19  
> 汇报主题：当前进展、统一产品决策、AI 交互入口与下一阶段计划

## 一、汇报摘要

目前产品的核心技术链路已经跑通：系统能够从**热搜榜、重点主题圈和未来事件**三类热点源获取信号，完成事件识别与聚合，并根据不同账号的定位产出对应内容。

当前阶段的判断是：系统已经从“验证链路能不能跑”进入“把结果做准、把内容做得可用、把运营体验做顺”的阶段。现阶段不再拆成多个独立系统，而是在一个统一产品中保持清晰的模块边界。这样既能复用 Event、账号、内容和结果数据，也能避免系统拆分带来的重复建设和联调成本。

老板此前提出的 **AI 交互入口已经完成入口设计和产品承载**。用户可以从统一入口发起调研、内容生成、修改和后续 Agent 工作流；下一阶段会继续把入口后面的 Agent 能力、操作权限和运行记录补齐，使其从“可进入”升级为“可稳定完成任务”。

接下来主要推进三项工作：

1. 优化现有热点到内容链路的准确性、去重、证据和运营体验。
2. 新增爆款视频内容拆解与复刻能力，把有效内容结构沉淀为可复用洞察。
3. 将内容生产从纯文字扩展为文字与图片协同生成。

## 二、目前已经完成什么

### 2.1 三类热点源已经进入统一链路

```text
热搜榜 ─────┐
重点主题圈 ──┼→ 事件识别与聚合 → 账号匹配 → 内容产出
未来事件 ────┘
```

目前已经验证：

- 热搜榜可以持续采集并触发事件处理。
- 重点主题圈可以提供垂直领域的内容信号。
- 未来事件可以提前进入监测和内容准备。
- 不同来源可以汇入统一的事件聚合流程。
- 聚合后的事件可以根据账号定位和 Content Skill 生成账号专属内容。
- 内容可以继续进入人工处理、发布回填和追踪链路。

### 2.2 当前完成的是“链路跑通”，不是“内容质量已经验收”

系统现在能够稳定走到内容产出，但还不能把“成功生成”直接等同于“内容可用”。当前仍需验证和优化：

- 事件与来源是否真正对应；
- 同一事件是否被重复触发；
- 多地区和多来源 Evidence 是否完整；
- 内容是否忠实于事实依据；
- 内容是否符合对应账号定位；
- 多条候选是否具有真实差异；
- 运营人员是否能快速找到当天需要处理的任务。

因此，下一阶段重点不是重新搭建主链，而是提高主链的正确性、内容可用性和运营效率。

## 三、为什么不做系统解耦

### 3.1 业务上是一条连续闭环

三个热点源虽然不同，但进入系统后共享同一组核心能力：

- Event 身份与版本；
- Fact 与 Evidence；
- 账号与 Content Skill；
- 内容候选、审核和发布状态；
- 内容表现和后续优化数据。

如果现在拆成多个独立系统，每个系统都需要重复建设账号、内容、权限、审核、状态和结果回流，并处理跨系统数据同步。这样会增加复杂度，却不会直接提高当前最重要的内容质量。

### 3.2 当前瓶颈不是系统容量，而是结果质量

目前尚未出现必须通过独立部署解决的容量、团队边界或故障隔离问题。当前真正影响产品验收的是：

- Event 是否准确；
- Evidence 是否完整；
- 是否发生重复响应；
- 候选内容是否可用；
- 运营工作台是否清晰。

把时间投入物理拆分，会延后这些核心问题的解决。

### 3.3 不拆系统不等于没有边界

我们采用的是：

**统一产品 + 模块化架构 + 标准接口 + 可替换 Agent/Skill/Connector。**

系统内部仍按能力区分热点接入、事件聚合、内容生产、发布追踪和效果学习。新增热点源通过 Connector 接入，新增运营规则通过配置实现，新增 AI 能力通过 Agent/Skill 注册和编排实现。

未来如果出现以下情况，再进行物理拆分：

- 某个模块需要独立扩缩容或独立可用性目标；
- 不同团队需要独立开发和发布；
- 故障隔离、数据合规或成本要求必须独立部署；
- 统一部署已经持续阻碍研发效率。

因此，我们不是放弃解耦，而是先做**业务和代码解耦**，暂缓没有收益证据的**系统和部署解耦**。

## 四、AI 交互目前做到什么程度

### 4.1 已完成

- 已经在统一产品中提供 AI 交互入口。
- 用户可以围绕事件、账号和内容任务进入 AI 协作。
- 入口可以承接后续的内容生成、修改、调研、解释和 Agent 工作流。
- AI 交互与 Event、Evidence、账号和内容任务处于同一个产品上下文中，不是独立聊天工具。

### 4.2 下一阶段补齐

- 将用户自然语言意图映射为具体 Workflow，而不只是返回文本。
- 明确哪些动作由 AI 建议、哪些由程序执行、哪些必须人工确认。
- 保存 Agent/Skill 版本、输入依据、输出、耗时、错误和人工决定。
- 支持失败重试、人工接管和运行结果解释。
- 增加内容质量评审 Agent，但不让 AI 自动批准高风险内容。

对外汇报口径应是：

> AI 交互入口已经进入产品，能够承接事件和内容场景；下一阶段重点是把入口后的 Agent 工作流和可追溯执行能力做完整。

不建议表述为“所有 Agent 能力已经完成”。

## 五、下一阶段工作

### 5.1 优化现有主链

重点解决：

- 修正事件来源与 Evidence 错配问题；
- 同一事件没有新事实时不重复触发内容任务；
- 完成和过期任务退出今日工作台，进入事件仓库；
- 合并和拆分只在真正不确定时进入 Human-in-the-loop；
- Future Event 保留官方网站 Evidence，未经人工或规则触发不进入响应 Event；
- 统一多语言榜单标题，同时保留原始语言；
- 统一 Signal、Candidate Event 和 Event 的进入边界；
- 让重点主题圈正式复用事件处理主链；
- 完整保留多地区、多榜单的 Evidence 关系；
- 建立内容可用性评审，而不只检查是否生成成功。

### 5.2 爆款视频拆解与复刻

新增链路：

```text
爆款视频样本
  → 获取标题、字幕、画面线索、互动和表现数据
  → 判断相对账号/同类内容是否异常优秀
  → Agent 拆解 Hook、结构、节奏、视觉、情绪和互动机制
  → 人工确认可借鉴与不可复制部分
  → 形成 Content Insight
  → 在新内容生成时选择性引用
```

这里的“复刻”是复刻有效方法，而不是复制原内容：

- 可以复刻选题角度、Hook 类型、叙事结构、信息节奏和视觉组织；
- 不复制原文、原视频、未经授权素材或未经核验事实；
- Content Insight 只能提供创作方法，不能替代 Event 的事实依据。

### 5.3 从文字生成扩展为文字与图片生成

内容交付从单一文案升级为组合内容包：

```text
Event Context + Account Skill + 可选 Content Insight
                         ↓
              文字候选 + 图片方案/成图
                         ↓
               人工审核与组合选择
```

首版建议支持：

- 文字：快讯、解释、观点、产品承接文案；
- 图片：单图事实卡、数据/概率卡、时间线和带品牌视觉的社媒配图；
- 文字与图片共享同一 Event、Evidence 和账号上下文；
- 图片中的数字、事实和产品信息必须来自可追溯数据；
- 保存 Prompt、模板、品牌资产和生成版本；
- 发布前仍由人工审核文字与图片组合。

## 七、建议的老板汇报结论

> 当前产品已经完成从三类热点源到事件聚合、再到账号内容产出的技术闭环，证明核心产品路径可行。我们下一阶段不会把精力投入到过早的系统物理拆分，而是保持一个统一产品，通过模块、Connector、配置和 Agent/Skill 实现内部解耦。这样可以优先解决事件准确性、证据完整性、重复响应和内容可用性问题。
>
> AI 交互入口已经进入产品，并与事件、账号和内容任务结合；下一步会继续补齐入口后的 Agent Workflow、人工门禁和运行记录。同时，产品会增加爆款视频拆解与复刻能力，并把内容生成从文字扩展到文字和图片，使系统从“发现热点并生成文案”升级为“理解什么内容有效，并持续生产可用的多模态内容”。
